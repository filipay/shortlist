**User's choice:** Dual-support with detection · retain the V1 machinery · V2 fixture slice + negative control · pin the version and assert it in the live lane.
**Notes:** The first two answers contradicted each other (dual-support needs the V1 machinery that "delete all V1" removes). The conflict was surfaced rather than papered over, and the user chose to **really support both**. D-54's "no adaptive client" still holds: that rule is about fuzzy-matching field *names within one contract*, whereas this is version-level selection. `contract.py` therefore carries two clearly-separated contract groups so neither silently absorbs the other's names.

## Deferred Ideas

- **Settings model picker (own phase).** New user-facing capability: let the user choose which model backs the project from Settings. UI + persistence + a discovery source. 07.1 preserves only the seam (`discover_models`, D-146). Open unknown: V2's `/api/model` / `/api/provider` return an empty array over HTTP for this directory while the CLI lists 40 models.
- **Residual prompt-injection risk — accepted, documented, revisit later.** V2 has no `system` field, so the frozen-system-prompt separation collapses into a single-prompt convention. Domain grounding still blocks fabrication of employers/titles/dates/bullets/skills, but a malicious listing could override the instructions to produce schema-valid-but-dishonest output. The user accepted this on condition it is documented (runbook + `AGENTS.md` security note + README) and revisited later — candidate fixes are the experimental per-session instructions endpoint (placement unconfirmed) or a plugin `context` hook (needs plugin files outside the repo).
- **Per-call served-model and token telemetry** — no longer observable under V2 `generate`; revisit if opencode exposes them again.
