# Phase 07.1: Migrate the LLM backend to the opencode V2 HTTP API - Context

**Gathered:** 2026-10-13
**Status:** Ready for planning

<domain>
## Phase Boundary

Make the app's LLM backend speak the **opencode V2 HTTP API**, so ranking, tailoring,
screening-answer drafting and CV fact extraction work again.

Trigger (live-verified): the app's pinned V1 contract is dead on the installed opencode
**2.0.26**. Every legacy root route (`/global/health`, `/doc`, `/session`, `/provider`, …)
now returns the web-UI SPA HTML, `POST /session` is a hard `405`, and the real JSON API
lives under `/api/…` behind HTTP basic auth. Every LLM call therefore fails with
`JSONDecodeError` (`llm_calls`: `status=error`, `attempts=0`, `model=None`) and the user sees
"Draft answers"/"tailoring" refusals.

**In scope:** the wire contract (both API surfaces + detection), the builders, the backend
client, config, the health/auth surface, the contract fixture + live lane, the runbook, and
the telemetry consequences.

**Out of scope:** any new user-facing capability. Notably a **Settings model picker** is a
separate phase (see Deferred Ideas) — this phase only preserves the seam it will need.

</domain>

<decisions>
## Implementation Decisions

### Server authentication
- **D-135:** The operator obtains the server password via the **documented V2 pairing flow** — `POST /api/pair` yields a single-use code, then `GET /auth/connect/{code}` returns a session token used as the password. (Chosen over scraping the auto-generated `server password …` startup log line, which is undocumented.)
- **D-136:** When the configured password is empty **or** rejected, the app **fails fast** — it does not attempt the call — and records a distinct auth-missing outcome. Consistent with D-08 (degraded-tolerant health) and D-52 (surface the full cause, never a bare badge).
- **D-137:** Auth failures get a **new `unauthenticated` error kind**, plus an `auth_configured` boolean on the `/health` opencode report, so the UI can say "auth missing / 401" rather than a generic error.
- **D-138:** The operator story is documented in the runbook, `.env.example` and the README. The app only ever **consumes** the password; it never generates or stores it.

### Structured output (now client-side)
- **D-139:** Keep **2 client-side schema retries** — `opencode_structured_retry_count = 2` becomes the client-side budget (keeps call cost and the D-52 taxonomy comparable to V1).
- **D-140:** A retry **feeds the first pydantic validation error back** into the re-issued prompt.
- **D-141:** Extraction **tolerates code fences and leading prose** — strip fences/preamble, take the outermost brace block, then hand it to `_salvage`.
- **D-142:** Salvage tolerance is **unchanged**: `TOLERATED_SCHEMA_ERRORS` stays exactly `{"missing","int_parsing"}` and `_salvage` is untouched. Widening it was rejected before because it substitutes field defaults and silently discards real answers (the G-07-7 hazard).

### Telemetry, model selection, discovery
- **D-143:** `llm_calls.model` records the **configured** `OPENCODE_MODEL` string — the column means *requested*, not *confirmed served*; provider and agent are NULL; server version comes from `GET /api/info`. — **Reversibility:** costly — the column's meaning changes for every row written from now on, so the docstring and any consumer must agree before historical rows are compared.
- **D-144:** **D-12 is re-scoped** to: record the configured model plus the server version for every call, and state plainly that per-call *served*-model and token identity is unavailable under the V2 `generate` contract.
- **D-145:** Model selection is proven by a **positive + negative live check** — a real `generate` returning a validated `ProbeResult`, and one call with a deliberately unknown model asserting it is rejected (proving the model field is honoured, not ignored).
- **D-146:** `discover_models` is **RETAINED, not deleted**, retargeted to V2's `GET /api/model` + `GET /api/provider`, preserving D-09's redaction guarantees and their tests. It is the seam for the future Settings model picker (see Deferred Ideas). — **Reversibility:** costly — deleting it later would require re-deriving the redaction controls and their tests from scratch.

### V1 ↔ V2 posture
- **D-147:** **Dual-support with runtime detection** — the backend detects which API surface the server exposes and speaks the matching contract. V1 servers keep working; V2 servers work for the first time. — **Reversibility:** costly — the pinned contract, the fixture and the runbook all carry two shapes, so collapsing to one later means re-deriving the V1 pins from source.
- **D-148:** V1-only constants and code paths are **retained** (reversing an earlier delete-all lean), kept grouped in `contract.py` so the two contracts stay distinguishable and neither silently absorbs the other's names. D-54's "no adaptive client" still holds — that rule is about fuzzy-matching field *names within one contract*; this is version-level selection.
- **D-149:** The contract fixture is rebuilt as a **hand-written V2 slice** of `/openapi.json`, **plus a negative control** asserting `json_schema`, `structured`, `outputFormat`, `retryCount` and `tool_choice` are **absent** — pinning "no server-side structured output" as a deliberate fact rather than an assumption.
- **D-150:** The observed server version is **pinned** in the fixture metadata and the runbook, and the operator-run live lane **asserts the running server matches one of the supported contracts** — so drift is caught by a test, not by a mysterious `JSONDecodeError`.

### the agent's Discretion
- **The detection mechanism itself** — how the app distinguishes a V1 server from a V2 one (probe path, ordering, caching, what happens on an ambiguous or partial surface) was not discussed and is left to research/planning. It must not depend on the SPA fallback returning 200 for everything.
- The exact wire shape of the `unauthenticated` classification and the `auth_configured` health field.
- Retry pacing/backoff between schema retries (there is no server-side `retryCount` any more).

</decisions>

<specifics>
## Specific Ideas

- The failure signature to reproduce in a test: `llm_calls` row with `status=error`, `attempts=0`, `model=None`, `latency_ms=None`, `error=JSONDecodeError` — the call never reached a model.
- The V1-must-fail evidence: every legacy root path returns the SPA HTML and `POST /session` returns `405`.
- The V2 send endpoint discovered by probing: `POST /api/session/{sessionID}/prompt` (send) vs `GET /api/session/{sessionID}/message` (read) — the design deliberately chooses `POST /api/session/{id}/generate` (`{prompt}` → `{data:{text}}`) instead, because it has **no tool-execution surface**.
- User's words on the injection boundary: *"we need to document it tho and in the future we probably need to address it. for now its fine"*.
- User's words on the model picker: *"i would like the user to be able to access and choose which model to use for their llm… this would be super helpful, especially for people running the free tier stuff"*.

</specifics>

<deferred>
## Deferred Ideas

### Settings model picker (own phase)
The user wants Settings to let them choose which LLM backs the project, explicitly for people
on free tiers. This is a **new user-facing capability** (UI + persistence + a discovery
source), so it does not belong in a backend-contract migration. 07.1 preserves the seam only
(D-146 keeps `discover_models` retargeted to V2). Open unknown for that phase: V2's
`GET /api/model` and `/api/provider` return an **empty array** over HTTP for this project
directory while `opencode models` (CLI) lists 40 models — the picker's data source must be
resolved there, not here.

### Residual prompt-injection risk — accepted, documented, revisit later
V2 has no `system` field on either `generate` or `prompt`, so the frozen-system-prompt
separation collapses into a single-prompt convention (frozen instructions first, schema block,
hard delimiter, explicit untrusted-data directive, existing per-part labels). Domain grounding
still blocks fabrication of employers, titles, dates, bullets and skills — but a malicious
listing could override the instructions to produce *schema-valid but dishonest* output. The
user accepted this for now, on the condition that it is **documented** (runbook + `AGENTS.md`
security note + README) and revisited in future — the candidate fixes being the experimental
per-session instructions endpoint (unconfirmed placement) or a plugin `context` hook (needs
plugin files outside the repo, breaking the self-contained constraint).

### Per-call served-model and token telemetry
V2's `generate` returns only `{text}`, so served model, provider and token counts are no longer
observable per call. Revisit if opencode exposes them again.

</deferred>
