<objective>
Close GAP 2 (WR-02): ground the bullet-targeting op fields at the validation boundary so a change-log entry can no longer describe a drop, reweight, demote or move that never happened.

Purpose: `_validate_patch` step 1 grounds every referenced id against `set(iter_fact_ids(facts))`, which also yields section, entry, skill, org, title and gap ids. So `drop_bullet(bullet_id="skill.python")` and `reweight_bullet(bullet_id="sec.skills")` validate cleanly, no-op in `_build_plan`, and still emit a `ChangeRecord` — the change log reports a drop that did not occur, which is exactly the honesty TAIL-08 promises. `check_bullet_conservation` cannot catch it because the id is neither a fact bullet nor a plan bullet. The fix belongs at the one place the grounding set is decided, not at each call site.

Output: `_validate_patch` with per-op-family grounding sets (`bullet_ids`, `section_ids`), the four bullet ops grounded on bullets and `ReorderSection` grounded on sections; and the regression tests that pin the rejection and the change-log honesty.
</objective>

## Observable truths a verifier should check

1. `apply_patch(facts, patch)` raises `UnknownIdError` for a bullet op whose `bullet_id` or `before_id` is a skill, section, entry, org, title or gap id.
2. `apply_patch` raises `UnknownIdError` for a `reorder_section` whose `section_id` is a bullet id.
3. A rejected patch produces no `RenderPlan` and therefore no `ChangeRecord`.
4. For a valid five-op patch, every `ChangeRecord` names a fact at its op family's locus: a `drop_bullet` record names a source bullet the plan no longer carries, and a `reweight_bullet`/`demote_bullet`/`move_bullet`/`reorder_section` record names an entity the plan carries.
5. Real bullet and section ids still validate and apply exactly as before.
</verification>
