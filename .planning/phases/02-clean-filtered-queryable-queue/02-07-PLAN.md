# Plan 02-07 — The queue you can actually search: full-text, new, stale, excluded

**As a** job-seeker with more listings than patience, **I want to** search the queue, see what is new since I last looked and what has gone stale, and reveal what was filtered out with the reason attached, **so that** I can find the jobs I care about without re-reading everything.

<objective>
Turn the Phase-1 listing table into the queue the phase promises: searchable, signal-bearing, and honest about what it is hiding.

Purpose: this is QUEUE-06, QUEUE-07 and FILT-03, and success criteria 2 and 4 of the phase. The Phase-1 queue renders every listing in one deterministic order with no search. This plan moves the query into a repository, adds FTS5 search with a mandatory safety transform, adds the watermark and staleness badges, and makes the excluded listings reachable with the rule that fired.

Output: `app/domain/search_query.py` (the pure FTS safety transform), `queue_repo.py` and `state_repo.py`, the rewritten queue route, three templates, and five test modules.
</objective>

- **D-42** — FTS5 `MATCH` over `title` + `company_norm` + `description` on the existing `listing_fts` external-content table, ranked by `bm25` **only when a query is present**; with no query the queue keeps the Phase-1 deterministic order `first_seen_at desc, id desc`. - **D-39** — "new since last visit" is a DB watermark (`queue_state.last_queue_view_at`), advanced when the queue page is opened, plus an explicit `Mark all as seen` action. A cookie was explicitly rejected. *(Reversibility: reversible.)*
- **D-40** — stale is `last_seen_at` older than `stale_after_days` **or** `is_active = false`; stale rows get a badge but stay searchable. Reuses existing columns; robust to partial runs and board pagination.
- **D-35** — "why was this excluded" is an inline `Show excluded` toggle on the queue: rejected listings appear dimmed with a chip naming the firing rule and a per-rule count; excluded listings are out of the default view and out of any future LLM spend.

### The three research findings this plan must respect (all verified by execution)

1. **Raw user text in `MATCH` raises.** These ordinary inputs all raised `sqlite3.OperationalError` against the real `listing_fts`: `-`, `a AND`, `"unbalanced`, `OR`, `*`, `NEAR(`, `runner-up`, `it's`. The `runner-up` case failed with `no such column: up`, and `it's` with `fts5: syntax error near "'"`. Wrapping each token in double quotes fixed every one.
2. **`bm25()` alone is not a deterministic sort.** Two rows with the identical score `-1.375e-06` came back `[3, 1]` from the `bm25()` query and `[1, 3]` from the `rank`-alias query. Every FTS ordering must end with a unique tie-break.
3. **The score is negative and more-negative means more relevant**; `bm25(listing_fts, 10.0, 5.0, 1.0)` accepts per-column weights in the FTS column order `(title, company_norm, description)`.

### Verified query shape to use verbatim

```sql
SELECT l.id, l.title, bm25(listing_fts, 10.0, 5.0, 1.0) AS score
FROM listing_fts
JOIN listings l ON l.id = listing_fts.rowid
WHERE listing_fts MATCH :match_expression
  AND l.is_active = 1
ORDER BY score, l.id DESC
LIMIT :limit OFFSET :offset
```

The no-query branch must **not** join `listing_fts` and must keep:

```sql
SELECT ... FROM listings l WHERE ... ORDER BY l.first_seen_at DESC, l.id DESC LIMIT :limit OFFSET :offset
```

## Flagged Assumptions (edge-probe coverage)

The phase's edge-coverage report left 28 rows `unresolved`. Those owned by this plan:

- **[QUEUE-06 · empty]** Result for an empty/single-element/`None` query. **Assumption:** an empty or whitespace-only query returns `None` from `build_match_expression`, and the service then takes the **no-query branch** and skips the `listing_fts` join entirely — it never issues `MATCH ''`. A single-token query still gets its `*` prefix. A `None` query parameter and an absent parameter are the same case. Asserted for `None`, `""`, `"   "` and a single token.
- **[QUEUE-06 · encoding]** Whose definition of length/equality applies? **Assumption:** tokenisation is `re.split(r"\s+", ...)` over Python `str` (Unicode code points) and `porter unicode61` does the stemming; this plan adds **no** second stemmer and no normalisation of its own, so the only case/encoding behaviour is the tokenizer's. A non-ASCII token is quoted like any other. Asserted with a `"café"` query and with the existing porter-stemming behaviour (`'managing'` matching a `"Quantum Manager"` row) preserved — the plan must not add its own stemming.
- **[QUEUE-06 · ordering]** When rows compare equal, is the order stable? **Assumption:** every FTS order ends `score, l.id DESC` (the unique tie-break), and a test fetches the same page twice and asserts an identical id sequence — this is the executable form of Finding 2 above and it must fail if the tie-break is removed.
- **[QUEUE-07 · unclassified — review manually]** Surfaced, not dropped. **Assumption:** "new" and "stale" are two **independent** badges, not a state machine — a listing can be both new and stale (newly ingested but already inactive), and neither badge suppresses the other. `NULL` watermark means "never viewed", so every listing is new. A staleness boundary at exactly N days is stale (`last_seen_at <= now - stale_after_days`). Asserted at N-1, N and N+1 with a controlled `now`.
- **[FILT-03 · unclassified — review manually]** Surfaced, not dropped. **Assumption:** the excluded toggle is a **view** over `listing_exclusions` for the listing set the queue would otherwise show, not a second page; a listing excluded in an older run but not in the latest still shows its latest exclusion reason only. Per-rule counts are grouped over the latest run so the chip's number matches what the run actually did. Asserted by excluding a listing in run 1, not excluding it in run 2, and checking the chip reflects run 2.
- **[FILT-03 · interaction between `Show excluded` and `Load more`]** Research Open Question 3. **Assumption:** **any predicate change resets `offset` to 0** — the `hx-get` URL carries `q`, `excluded`, `hidden`, `scope` and `offset`, and the template resets `offset` whenever a predicate changes, because page N of a different filtered set is meaningless. Asserted in the route test by changing the toggle and checking the returned fragment's Load-more link carries `offset=0`.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| the search box (untrusted text) → the FTS5 parser | a typed query is an expression, not a literal; malformed input raises against the database and 500s the page |
| listing text (untrusted) → the browser | titles, companies and descriptions from job boards are rendered into the queue |
| the query string (user-controlled) → filters and paging | `excluded`, `hidden`, `saved`, `scope` and `offset` are all client-supplied |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-26 | Tampering / Denial of Service | FTS5 `MATCH` built from user text | high | mitigate | `build_match_expression()` quotes every token with FTS5's own literal escape and returns `None` for an empty query so the FTS join is skipped entirely; `MATCH` takes a bound parameter only (`:match_expression`), never an f-string; the tests run all eight verified-hostile inputs through the real parser against the migrated database. |
| T-02-27 | Tampering (stored XSS) | `queue_list.html` / `_listing_row.html` rendering listing fields | high | mitigate | Jinja autoescape with **no `|safe`** on any listing-derived value; badges and chips are server-rendered text; no remote script or stylesheet (`tests/test_no_cdn.py`); the ingestion sanitiser already strips HTML and PII from descriptions. |
| T-02-28 | Denial of Service (self) | page size and paging | low | mitigate | `limit` comes from `settings.queue_page_size`, never from the request; `offset` is parsed as an integer with a bounded default; a predicate change resets `offset` so an attacker cannot force deep scans by alternating filters; the FTS order is indexed by `bm25` with a unique tie-break. |
| T-02-29 | Repudiation | the new-since watermark | medium | mitigate | The watermark lives in a single database row, is advanced only by opening the queue or by the explicit `Mark all as seen` action, and never moves backwards; the "what is new" claim is therefore auditable and restart-safe rather than a cookie the client controls. |
| T-02-30 | Information Disclosure | `Show excluded` revealing listings the default view withholds | low | accept | Single local user with no auth by design (v1); the toggle is an intentional product feature (D-35), and excluded listings are explicitly out of future LLM spend. Recorded so the disclosure is a decision rather than an oversight. |

Residual risk accepted: `OFFSET` paging degrades on a very large corpus. The corpus is one person's job search; keyset paging is the documented upgrade path in the repository docstring, not needed for v1.
