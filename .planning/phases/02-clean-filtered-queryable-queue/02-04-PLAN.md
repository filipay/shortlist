# Plan 02-04 — Tier-2 dedup and merge: the same job found twice becomes one listing

**As a** job-seeker who reads one queue every morning, **I want to** see a job that LinkedIn and Indeed both list as a single entry, with the merge recorded and the second copy kept, **so that** I never read the same role twice and I can always undo a merge that was wrong.

<objective>
Wire the thinnest true end-to-end merge: two sources persist their rows, the run scores candidate pairs, one pair merges, the merge is audited with the survivor's pre-merge snapshot, and the run's `deduped_count` reports it.

Purpose: this is QUEUE-03 and the first half of success criterion 1. Tier-1 already prevents the *same source* duplicating a listing (the two-key upsert); Tier-2 is what makes a *cross-source* duplicate collapse. The failure mode to design against is not "fails to merge" but "merges two genuinely different roles", which is silent and destroys a real job — so the gate is component-based and safety-biased, and every merge is reversible.

Output: `app/domain/dedup.py` (pure decisions), `app/db/repositories/dupe_repo.py` (the only place the merge SQL lives), `app/pipeline/dedup_stage.py`, the stage insertion in `run_pipeline()`, and three test modules.
</objective>

### Decisions this plan implements

- **D-30** — Tier-2 dedup runs as a **post-persist stage inside `run_pipeline()`**, after all sources' rows are persisted, because a cross-source candidate pair needs both rows to exist before it can be scored.
- **D-31** — `rapidfuzz` over the normalised `(company, title, location)` tuple, with `listings.blocking_key` used to narrow candidates and **θ a `Settings` value**. The *algorithm* choice inside D-31 is the agent's discretion: this plan makes the **component gate primary** and the fuzzy score a quality signal, because `fuzz.token_set_ratio` is verified subset-forgiving (it returns `100.0` for `"fuzzy was a bear"` against `"fuzzy was a bear but not a dog"`), so `"Software Engineer"` and `"Senior Software Engineer"` would score 100 and reproduce the exact failure `PITFALLS.md` P3 warns about. `token_sort_ratio` is used as the gate score; `token_set_ratio` is computed for the log only and never decides.
- **D-26** — the merged twin is retained in full and surfaced later in the job detail; this plan writes `listing_dupes.snapshot_json` so the record exists.
- **D-27** — the first-seen listing stays canonical and only blanks are filled; nothing non-null is ever overwritten. *(Reversibility: costly — switching to source-priority or per-field precedence later rewrites already-merged listings; the snapshot makes the data recoverable, but the rule change touches every merged row.)*
- **D-28** — revert is a full undo plus negative memory; this plan implements the negative-memory **pre-check** (the revert action itself is plan 02-06).
- **A5 (research assumption — explicitly surfaced, because this amends `research/ARCHITECTURE.md` §8.3)** — `listing_sources` rows **stay on the absorbed twin** and are **not** re-pointed at the survivor. §8.3 says "all `listing_sources` rows move to the surviving `listing_id`"; this plan deliberately diverges, because moving them makes revert a data migration rather than a flag flip and destroys the absorber↔twin provenance the audit view needs. "Merged from N sources" is derived through the `listing_dupes` join instead. The trade: a query that expects every source row to hang off the visible listing must go through `listing_dupes` — which is exactly what plan 02-06's Merges view and the queue read model do.
- **D-36** — exclusions and merges are per-run observations; a merge is scored from scratch every run.
- **D-46 / D-24** — `app.domain.*` imports no I/O (`rapidfuzz` is permitted; `sqlalchemy` is not); settings, never constants.

## Flagged Assumptions (edge-probe coverage)

The phase's edge-coverage report left 28 rows `unresolved`. Those owned by this plan:

- **[QUEUE-03 · unclassified — review manually]** The probe could not classify the residue. **Assumption:** the unclassifiable part is the *merge-rate band*. No test asserts a rate; the rate is a reported statistic (plan 02-06) and θ is tuned against a real corpus via a manual-only verification (`02-VALIDATION.md`, "Dedup threshold θ tuned against the first real corpus"). Asserting a band would freeze a number this phase explicitly must not freeze.
- **[QUEUE-03 · subset pathology]** Resolved by research, encoded as an assumption with its citation. `fuzz.token_set_ratio` returns `100.0` when one string is a subset of the other "regardless of extra content in the longer string" (`[CITED: https://github.com/rapidfuzz/rapidfuzz/blob/main/docs/Usage/fuzz.rst]`). **Assumption:** token-set ratio is never the gate; the component gate plus `token_sort_ratio >= θ` is the gate, and the token-set score is recorded in the log as a diagnostic only.
- **[A5, RESEARCH Assumptions Log]** `listing_sources` rows stay on the absorbed twin rather than moving to the survivor. **Assumption:** this amends `research/ARCHITECTURE.md` §8.3 deliberately, and every consumer of "which sources saw this job" must join through `listing_dupes`. Surfaced in this plan's decisions block rather than diverging silently.
- **[QUEUE-03 · ordering of merges within a run]** Unresolved by research. **Assumption:** candidate pairs are processed in a deterministic order — ascending `(survivor.first_seen_at, survivor.id, twin.id)` — and once a listing has been absorbed it is removed from the candidate pool, so a three-way duplicate produces two merges onto the first-seen survivor rather than a chain. The chain rule matters: the earliest-seen listing is always the survivor (D-27).
- **[QUEUE-03 · a `posted_at` that is `None`]** **Assumption:** the posted-window blocking rule **includes** a pair when either side's `posted_at` is `NULL` (the window narrows candidates; it never silently excludes an unknown, consistent with the A2/A3 policy), and the company block plus the component gate still apply.

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-10 | Tampering (data loss) | `apply_merge` field fills | high | mitigate | Fill-blanks-only over `_LISTING_FIELDS`: a value is written only when the survivor's current value is `None` or an empty string; `title`, `company_id`, `canonical_url`, `first_seen_at` and `content_hash` are not in the tuple and are therefore structurally unreachable; the absorbed row is never deleted or deactivated. |
| T-02-11 | Repudiation | a merge with no or partial audit trail | high | mitigate | Exactly one `ListingDupe` row per merge, written in the same transaction as the field fills, always carrying `method`, `score`, `merged_at` and the pre-merge `snapshot_json`; `listing_dupes` is INSERT-only on this path, so revert (plan 02-06) is a flag flip and nothing is lost. |
| T-02-13 | Tampering | revert undone by the next run (D-28 negative memory) | high | mitigate | `reverted_pairs` reads reverted rows in **both orientations** and the stage filters those pairs before scoring, so an automatic merge cannot reverse a user's revert. The plan-02-01 unique index covers the same-orientation re-insert; the reversed case is covered by the pre-check because SQLite ignores `NULL` in a unique index. |
| T-02-12 | Denial of Service (self) | fuzzy scoring over an unbounded candidate set | medium | mitigate | Candidates are narrowed by an indexed `company_norm` equality first, so the block is one company's postings rather than the corpus; the posted window narrows further; a group of one is dropped before any scoring. No all-pairs comparison exists anywhere in the module. |
| T-02-14 | Tampering | FTS index drift after a merge's field fill | medium | mitigate | All fills go through the `listings` ORM row so the `listings_au` trigger fires; a merge-then-search assertion in `tests/db/test_dupes.py` proves it, extending the Phase-1 round-trip guarantee. |
| T-02-15 | Repudiation | a disabled or unknown rule silently treated as applied | low | accept | Out of this plan's scope (rules are plan 02-05/02-08); recorded here so the same class of silent drop is not assumed away in the merge path, where the equivalent control is the audited `listing_dupes` row. |

Residual risk accepted: a merge that is *wrong but plausible* (two genuinely different roles at one company with near-identical titles and no grade token) remains possible. The mitigations reduce its probability and make it fully reversible with a retained snapshot; the product decision (D-25) is that automatic merging is worth that residual risk because a confirmation queue re-introduces the daily-loop cost the project exists to remove.
