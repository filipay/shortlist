### The post-completion fix arc (tasks 7–8) — why it exists

The cycle closed at `80a9b33` with the reset nominally complete, and every review had passed it. The operator then ran it against the **live** database and got "Internal Server Error", with nothing deleted; Dismiss and the Apply links worked. Root cause, proven two independent ways against the live schema and then reproduced in a test:

- `listing_events` carries a `BEFORE DELETE` trigger from migration 0001 (`RAISE(ABORT, 'listing_events is append-only')`) **and** a `NO ACTION` FK to `listings`. Its rows can therefore neither be deleted (the trigger aborts) nor left behind while `listings` are deleted (the FK refuses).
- `RESET_DELETE_ORDER` lists `listing_events` **first**, so the very first `DELETE` aborted; SQLAlchemy raised `IntegrityError`, the route's narrow `except (ResetRefused, sqlite3.Error, OSError)` did not catch it, and it escaped to Starlette as a bare 500 with the session never rolled back.

This was a **spec-level bug, not an implementation slip**: the spec's step 5 and its "Tables deleted" row both named `listing_events`, so the code faithfully implemented an impossible order. Every review missed it for one reason — the reset test corpus seeded **zero** `listing_events` rows, and a per-row `BEFORE DELETE` trigger never fires on an empty table, so the delete silently succeeded and the "every table is 0" assertion was **vacuous for exactly the one table that cannot be emptied**. The fix re-ran the deletes against a corpus seeded into every table, which reproduced the exact production abort in a test.

The remediation also surfaced a second, subtler defect: with the app's original engine, `session.rollback()` did **not** restore a dropped trigger, because pysqlite does not open a transaction for DDL and implicitly COMMITs before it. Left alone, a reset that failed mid-delete would have left the append-only invariant **permanently disabled**. That is why `c16023a` also changes the engine, and why the engine change is recorded as a decision in its own right (task 8).

### Decisions this plan implements

- **D-41** — Save and Hide are distinct actions written as **append-only `listing_events`** with current state projected from the latest event; hidden listings leave the default queue and are reachable through the `Hidden` filter with one-tap undo; **the Phase-1 append-only triggers are reused unchanged**. Dismiss extends exactly this: one `hide` event per listing through `append_event`, no new event type (a seventh type would have needed a migration to widen the `listing_events.event_type` CHECK), and `Unhide` still reverses a single row.
- **D-39** — the queue's watermark and the explicit **"Mark all as seen"** action. Dismiss is the second bulk control on the same toolbar and mirrors `queue_mark_seen`'s conventions: `Depends(current_user)`, `hx-post` carrying `page.query.query_string()`, `hx-target="#queue-list"`, `hx-swap="innerHTML"`, and a read-after-write so the returned fragment already reflects the action.
- **D-46** — the locked stack: Jinja2 + HTMX + Alpine + Tailwind with **no CDN**, and **`current_user` on every route with no `user_id` columns in v1**. Both new routes declare the seam; every new class token has a rule in the committed `static/vendor/app.css`; no remote asset is referenced.
- **D-47** — migration 0001 already shipped `listing_events` with its append-only triggers, `listings.canonical_url`, `listing_sources.source_url`/`canonical_source_url` and `runs.status`. That is why this cycle needed **no schema migration at all**, and it is also the origin of the reset's one real constraint: `listing_events` rows can neither be deleted (the `BEFORE DELETE` trigger the same migration installs) nor left behind (the `NO ACTION` FK to `listings`), which is what the post-completion remediation in tasks 7–8 resolves. No migration was added to fix it either: the trigger is suspended and re-armed inside the reset's own transaction instead.
- **The engine change (task 8) is not a phase-2 CONTEXT decision.** It has no `D-NN` and is not derived from `02-CONTEXT.md`; it is a new, deliberate decision taken during remediation and recorded where the project records such things — `docs/implementation-notes.md` §4, "Engine transaction semantics — a deliberate change". It is cited here by name rather than given a decision ID it never had.
- **Phase-1 D-21 (no authentication in v1)** — the premise behind the reset's CSRF posture, recorded in `app/api/settings.py`'s module docstring: with no ambient credential a cross-site request has nothing to abuse, so the route is not CSRF-exploitable today, and it becomes one the moment session auth lands.

## Flagged Assumptions (edge-probe and known gaps)

Every item below is a shipped behaviour or a recorded limitation from the change record — surfaced, not dropped:

- **A dismissal above the ceiling is refused but not visibly.** `_DISMISS_LIMIT` is 10,000; above it `_dismiss_over_limit()` returns a 400 whose fragment htmx 2.0.10 discards (the vendored build ships `responseHandling:[{code:"[45]..",swap:false,error:true}]` and the app wires no `htmx:responseError` handler). **Assumption:** leaving it is the right call — the trigger is far above any realistic queue, the behaviour writes nothing (strictly safer than the truncation it replaced), and the correct repair is an app-wide htmx error handler rather than a one-off 200 on this endpoint. Recorded as a follow-up.
- **The `VACUUM INTO` destination is interpolated as an escaped SQL literal**, not bound. **Assumption:** safe today and left alone — the path is server-derived (`session.get_bind().url.database` plus a `strftime` timestamp) with no request-controlled component, and single quotes are doubled. The comment in `snapshot_database` says so rather than overstating the guarantee.
- **The confirmation token is an affordance, not a security control.** `DELETE` is rendered into the page in plain text. **Assumption:** the snapshot is the real mitigation, and the token exists to stop a fat finger or a prefetch. The route requires `POST` for the same reason.
- **Two cosmetic test-strength items stand.** `tests/api/test_settings_page.py`'s deleted/kept assertion is built from the same constants the template renders, so it proves the template echoes them rather than that they are right; and one `.danger-card button[type="submit"]:hover` declaration restates its non-hover values and only adds `filter: brightness(0.9)`. **Assumption:** neither blocks; both are recorded rather than silently fixed.
