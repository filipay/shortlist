# Plan 02-10 — Run history: one row per run, and an answer for an empty queue

**As a** job-seeker who needs to trust the pipeline, **I want to** see what each run did, what it found, and — when my queue is empty — exactly why, **so that** a quiet morning is explained instead of mysterious.

<objective>
Give the runs data a real surface: a history page with the persisted reason, the counts behind it and the bounded stage log, plus a last-run strip on the queue.

Purpose: this is RUN-04 and the rendering half of RUN-03, and success criterion 5 of the phase. Plans 02-04 and 02-05 filled `runs.fetched_count`, `deduped_count`, `filtered_count`, `reason`, `reason_counts_json`, `stage_log_json` and `criteria_snapshot_json`; nothing reads them yet. Until they are visible, "why is the queue empty today?" is still answered by opening a database — which is the exact failure `PITFALLS.md` P9 names.

Output: `run_repo.py` (the history read model), `GET /runs` and its template, the last-run strip on the queue, and two test modules.
</objective>

### Decisions this plan implements

- **D-43** — a dedicated `/runs` page: one row per run (started/finished, trigger `manual|schedule`, per-source fetched, `deduped_count`, `filtered_count`, errors, duration), expandable to detail — plus a compact **last-run strip on the queue** linking there. *(Reversibility: reversible.)*
- **D-44** — a thin or empty queue is explained by the persisted structured reason plus counts plus a rendered sentence, with a **collapsible raw stage log**. This plan renders what plan 02-05 persisted; it computes nothing new.
- **D-45 / A6** — one `runs` row per trigger, with per-search sections inside the criteria snapshot and the reason counts. The history page therefore shows **one row per run**, and the per-search detail appears inside the expansion.
- **D-46** — Jinja + HTMX + Alpine, vendored assets, no CDN.

### Interfaces to reuse (extracted — do not re-derive)

From `app/api/runs.py` (this plan extends it):
- `render_run_fragment(request, run, source_counts) -> str` — renders `_run_status.html`. D-43 says the queue strip reuses **this** renderer rather than a parallel one.
- `router`, `TEMPLATE_DIR`, the module-level `Jinja2Templates`, and `TERMINAL_STATUSES`.

- Every route declares `user: User = Depends(current_user)`.

From `app/db/repositories/source_repo.py`: the repository contract — explicit `AsyncSession` first positional, frozen read models, deterministic ordering **ending in a unique tie-break**, never commits. `get_source_health` is the closest analog: a read model joining two tables with `order_by(Run.started_at.desc(), Run.id.desc()).limit(RECENT_RUN_LIMIT)`.

From `app/db/models.py`: `Run` (`id`, `search_id`, `trigger`, `started_at`, `finished_at`, `status`, `source_counts_json`, `fetched_count`, `deduped_count`, `filtered_count`, `ranked_count`, `llm_calls`, `llm_tokens`, `errors_json`, `reason`, `reason_counts_json`, `stage_log_json`, `criteria_snapshot_json`), and the CHECKs `ck_runs_trigger` and `ck_runs_status` (`running`, `done`, `failed`, `partial`).

From `app/domain/run_reason.py` (plan 02-05): `REASONS`, `RunCounts`, `compute_empty_reason`, `reason_sentence`. `reason_sentence` is what turns the persisted reason plus counts into a displayed sentence — call it in the read model, never in the template.

From `app/db/repositories/exclusion_repo.py` (plan 02-05): `excluded_counts_for_run`, for the per-rule breakdown shown in the expansion.

From `app/web/templates/html/queue.html` (plan 02-07): the page shell, the `#run-control` block and the `#run-status-slot` element. The last-run strip is added to this page. The pinned Phase-1 assertions (`hx-post="/runs"`, `id="run-status-slot"`, `0 listings`, `No listings yet`) must keep passing.

### Pattern 4 — persist the decomposition, compute the aggregate

`runs.reason_counts_json` and `runs.stage_log_json` are the artifacts; the sentence is derived at render time from the persisted reason and counts. A changed count changes the sentence without any migration, and a historical run's sentence never drifts because it is always derived from that run's own row.

## Flagged Assumptions (edge-probe coverage)

The phase's edge-coverage report left 28 rows `unresolved`. Those owned by this plan:

- **[RUN-04 · unclassified — review manually]** Surfaced, not dropped. **Assumption:** run-history **retention and pruning are out of scope for this phase** — no run row is ever deleted and no pruning job exists. The page bounds what it renders with a `limit` (a module constant or a `Settings` value, documented) ordered newest-first, so an unbounded history cannot make the page slow. Pruning is recorded as a Phase-8 operations item.
- **[RUN-04 · ordering]** When two runs compare equal, is the order specified? **Assumption:** `(started_at DESC, id DESC)` — newest first, with the unique `id` as the mandatory tie-break. Two runs started in the same second are common when a user clicks twice, and `started_at` alone is not unique. Asserted by driving two runs in one test and comparing the rendered order across two requests.
- **[RUN-04 · empty]** The page with no runs at all. **Assumption:** an explicit empty state that names the run trigger and links to the queue's run control, not a blank table. Asserted on a fresh database.
- **[RUN-04 · idempotency]** Is the page safe to request repeatedly? **Assumption:** the surface is read-only; two identical `GET /runs` requests with no intervening run return identical bodies. Asserted by comparing two responses.
- **[RUN-04 · boundary]** A run that never finished (`finished_at` is `NULL`, status `running`). **Assumption:** the row renders an in-flight state and a duration of `None` — never `0s`, which would read as "finished instantly". Asserted by creating a `running` run row directly and checking the rendered body.
- **[RUN-03's rendering half · adjacency and precision]** Which persisted numbers the sentence may cite. **Assumption:** the sentence is generated by `reason_sentence` from `reason_counts_json` only, so the page cannot invent a number that the run did not persist; a test asserts the rendered sentence contains the same integer that appears in the persisted counts for `all_filtered` and `nothing_new`. No floating-point arithmetic is performed in the read model or the template.

### Not in this plan

No scheduling, next-run display or health-in-the-UI (Phase 8). No change to how a run is triggered, executed, or how its counters are written (plans 02-04 and 02-05). No log-file or `structlog` viewer — the stage log is the bounded JSON the run persisted.
