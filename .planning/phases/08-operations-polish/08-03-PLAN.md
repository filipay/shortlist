# Plan 08-03 — The tool runs itself, once a day, exactly once

**As a** job-seeker who does not want to remember to press a button every morning, **I want to** set a daily time and timezone and have the pipeline run itself once at that time without ever doubling up or back-filling a missed day, **so that** the queue is waiting for me when I open it.

> **MVP framing note.** The ROADMAP `**Goal:**` line for Phase 8 is an outcome, not a user-story sentence; the story above is derived from it plus PROJECT.md's Core Value and recorded rather than invented, matching the Phase 4 precedent.

<objective>
Ship the whole scheduling slice end to end: the singleton schedule document (migration 0008), the repository that owns its SQL, the in-process scheduler with a persistent job store wired into the app lifespan, the settings form that configures it without a restart, the argument-free scheduled target that reuses the existing pipeline, the overlap guard that APScheduler cannot provide, the skip-and-surface record, and the boot-time reconciliation of stale run rows.

Purpose: RUN-05 asks for recurring runs; PLAT-06 asks that they be single-worker safe and survive a restart. The phase's whole reason for scheduling late is that a scheduled run over an unstable pipeline hides failures — so the skip-and-surface contract (D-154) is not decoration, it is the feature's honesty mechanism: a missed or skipped run must be *visible*, never silent.

Output: migration 0008 and the `OperationsConfig` model; `operations_config_repo`; `app/jobs/scheduler.py`; the lifespan wiring; `POST /settings/schedule` and the `Schedule` settings card; the scheduler's own test lane; and the compose-smoke runbook extended with the persistence step.

**MVP framing of the acceptance test:** after Task 1 a user can set a daily time and see exactly one job registered; after Task 2 a scheduled fire actually runs the pipeline once, and refuses to overlap a manual run; after Task 3 a restart preserves the schedule (and its past-due fire time) and the feature degrades instead of breaking boot.
</objective>

### Decisions this plan implements

- **D-151** — one global schedule, not per-search. It runs the pipeline exactly as the manual trigger does: no search id, i.e. the union of all enabled searches. The existing `searches.schedule_cron` column stays unused and unpopulated; it is not the storage for this feature and must be left alone.
- **D-152** — the user configures the time-of-day and the timezone on the Settings page; a cron string is a fine internal representation but the user never types one. Days-of-week selection is out of scope.
- **D-153** — the schedule lives in a new singleton configuration row, runtime-editable with no restart, shaped like `RankingConfig`/`ApplyConfig`: `id = 1` pinned by a named CheckConstraint, a JSON payload, `updated_at`. It must be shaped so a future `user_id` column can be added, and no such column exists today (D-21).
- **D-154** — missed runs are skipped, surfaced, and never overlapped. A run missed by more than the grace window is skipped outright, never back-filled, and its absence is surfaced. A trigger that fires while a run is in flight skips and records why.
- **D-168** — the per-category retention thresholds live in the same singleton row. This plan creates the `retention_json` column; plan 08-05 is its reader and writer.
- **Orchestrator decision 6** — the table is named `operations_config` and mirrors `apply_config_repo` line for line; migration 0008 mirrors `0004_ranking_config.py`.
- **Orchestrator decision 7** — a missed or in-flight skip is recorded as JSON on the operations row, never as a new `runs` row and never as a fifth run status: migration 0008 must not batch-recreate `runs`, which is the exact hazard `test_upgrade_populated_0001_to_head` exists to catch.
- **Orchestrator decision 4** — boot-time reconciliation of non-terminal run rows is in scope: without it a cancelled run keeps the running status forever and blocks both the reset guard and every future scheduled run.

### Non-negotiable mechanics (verified against the pinned 3.11.3 source during research — do not re-derive)

1. **`AsyncIOScheduler`, never `BackgroundScheduler`.** The threaded scheduler's executor calls the callable synchronously, so an `async def` target returns a coroutine that is never awaited: the job reports success and runs nothing.
2. **The job target is module-level, argument-free and `async def`.** APScheduler serialises the callable as a module-qualified text reference and pickles `args`/`kwargs`; a lambda, a closure, a bound method or a non-picklable argument fails at `add_job`, which under the boot contract degrades the scheduler to unavailable and the feature silently does nothing.
3. **Create-if-absent at boot, never unconditional replace.** Re-registering a persisted job at startup recomputes its next fire time to the next *future* one and overwrites the stored state, which makes the missed-run event unreachable and silently kills D-154's "its absence IS surfaced".
4. **The in-flight guard is a database read, not `max_instances`.** `max_instances=1` counts only APScheduler's own submissions.
5. **`start()` must be called from inside the running loop** (the lifespan is), and `shutdown()` is synchronous and raises when the scheduler is not running, so the idempotency guard is required.

### Gate context the executor must respect

`.planning/config.json` sets `workflow.human_verify_mode = "end-of-phase"`, so this plan emits no mid-flight human-verification checkpoint; the operator-run persistence step lives in `docs/runbook-compose-smoke.md` and is harvested at end of phase. `workflow.auto_advance` is `false`.

No health page (plan 08-04), no pruning (plan 08-05), no responsive CSS (plan 08-02). The `retention_json` column exists from this migration but is neither read nor written here.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| the browser form → the stored schedule document | `time` and `timezone` arrive from the browser; a raw value must never reach the trigger or any statement |
| the process → its own restart | The persisted schedule and fire time are the only thing that survives; an unconditional re-registration at boot silently destroys the missed-run signal |
| APScheduler's executor → the async pipeline | There is no direct trust boundary, but the callable and its arguments are serialised into a third-party table, so their shape is a hard constraint |
| a scheduled run → a concurrent manual run | Both write `runs` rows and spend LLM budget; the database predicate is the only thing that can see both |
| the library's job store → our schema contract | The job store creates its own table outside Alembic, so the schema-drift guard must exempt it deliberately |
