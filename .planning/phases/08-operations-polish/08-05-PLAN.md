# Plan 08-05 — Payments on the retention debts, with nothing destroyed silently

**As a** job-seeker whose database and artifacts directory grow every day, **I want to** choose a category of old records and an age, see exactly what would be deleted and how much disk it frees, and only then delete it, **so that** the tool stays fast and small without ever losing something I still need.

> **MVP framing note.** The ROADMAP `**Goal:**` line for Phase 8 is an outcome, not a user-story sentence; the story above is derived from it plus PROJECT.md's Core Value and recorded rather than invented, matching the Phase 4 precedent.

<objective>
Pay down the retention debts earlier phases deliberately deferred: ship a manual, per-category, per-threshold prune over the run history and its stage logs, the tailored CV artifacts (rows and files), the source request log, and inactive or stale listings — behind a dry-run preview, a separate confirm, an audit line, and four hard guards that hold even under an aggressive threshold.

Purpose: the ROADMAP's own notes and three earlier phase comments name this as Phase 8 work — the artifact repository says "retention/pruning is deliberately Phase 8 and is not implemented here", the run repository's history limit says "pruning is a Phase-8 operations item", and the reset route records the known gap that deleting artifact rows leaves orphaned files on disk. Two of the four categories protect a *reader* rather than a user: the runs floor and the ledger exist so the health page's run-derived badge and the Adzuna verdict keep their inputs and so the spend ceilings keep working (D-165(1) and (2)). That linkage with plan 08-04's surface is why this plan carries RUN-07: the guards are the same invariant the health page depends on, and a page that shows a verdict while the prune silently starves its inputs would be a lie.

Output: `app/db/repositories/retention_repo.py`, the two prune routes on the settings module, the danger-zone prune card, and the guard suite.

**D-163** fixes the exact scope: there are four prunable categories — the run history with its stage logs, the tailored CV artifacts (the rows **and** the `.tex`/`.pdf` files on disk), the source request log, and inactive or stale listings — and the user chooses which category to prune and how old a record must qualify. Pruning is therefore per-category and per-threshold, never one global switch.

### The D-164 amendment (recorded, not implied)

D-164 says the audit logs are never pruned. D-167 says pruning a stale listing is a hard delete of the listing **and everything hanging off it**. Those two cannot both hold literally: `listing_events.listing_id` is NOT NULL with a no-action foreign key to `listings`, a `BEFORE DELETE` trigger makes the event rows undeletable, and foreign keys are enforced on every connection — so a listing that has any event row cannot be deleted while the trigger stands.

**The resolution is C2(b) from research, taken as an orchestrator decision this session.** The reset route already ships a tested mechanism that drops the trigger, performs its work, and re-arms it inside one transaction, and the engine makes DDL transactional. This plan reuses those exact two functions for the listing prune and records the amendment to D-164 explicitly: *the audit logs are never pruned **except** by the deletion of their parent listing, which is itself a user-confirmed, previewed, snapshotted, one-way action.* The research also notes the reset route has no assertion that the trigger comes back; this plan adds one, and it is the assertion the reset itself lacks.

The alternative — restricting the stale-listing category to listings that were never touched at all — was rejected because it makes the category nearly useless and the preview would honestly report a count of almost zero.

### Non-negotiable mechanics

- **The delete ordering.** `llm_calls.run_id` is a nullable no-action foreign key to `runs`, and guard 2 forbids pruning the ledger, so the runs category must delete its children first and then null the ledger's run reference rather than deleting those rows. `scores` and `listing_exclusions` reference a run with a not-null or nullable foreign key and must go before the run. A naive delete of `runs` fails at run time with a foreign-key error, and that failure would surface only at the operator's confirm step.
- **`queue_state` is not per-listing.** It is one global watermark row with no listing column. The per-listing children that actually need deleting are the scores, the source provenance rows, the exclusions, both sides of the dupes audit, the CV artifacts, the CV drafts and the screening drafts. Deleting the global watermark per listing is not a thing.
- **Sizes live on disk.** The database has no size column, so the preview's byte total comes from `Path(...).stat().st_size` over the selected rows, skipped and reported for a missing file, never a database sum.

### Decisions this plan implements

- **D-163** — the four prunable categories, chosen per-category and per-threshold by the user.
- **D-164, amended** — the audit events are excluded except by the deletion of their parent listing (the carve-out above, recorded as an amendment).
- **D-165** — four hard guards hold even under an aggressive threshold: a floor of recent runs; the call ledger is never pruned; an artifact linked to an application is never pruned; the newest successful artifact per listing is never pruned.
- **D-166** — pruning is manual only: a danger-zone control, a dry-run preview with counts and size, a separate confirm, an audit line, and no automatic pruning on the scheduled run.
- **D-167** — pruning a stale listing is a hard delete with an accepted, documented consequence: the upsert key goes with it, so a re-posted job returns as a brand-new listing and prior dismissals are gone.
- **D-168** — the per-category age thresholds live in the same singleton row as the schedule, as a JSON payload.
- **Orchestrator decision 3** — the source-request-log category carries its own run-floor guard: rows whose run is inside the retained floor survive.
- **Orchestrator decision 5** — snapshot the stale-listing category only; the regenerable categories are not snapshotted.
- **Orchestrator decision 8** — treat the phrase "its queue_state" in D-167 as a wording slip for the per-listing child tables; there is no per-listing global watermark.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| the browser form → the delete statements | A category and an age arrive from the browser and select what is destroyed |
| the database rows → the filesystem | Artifact paths stored in rows are unlinked; a hand-edited or legacy row could point outside the artifacts directory |
| the transaction → the append-only invariant | The listing carve-out suspends a tamper-evidence trigger, so the window in which it is down must be inside one transaction |
| the destructive route → a prefetch or link | Both steps are POSTs, and the confirm is reached only through the preview |
| the retention floor → the readers downstream | The ledger and the run floor protect the spend ceilings and the health page's inputs |

| T-08-26 | Tampering (destructive action from a GET or prefetch) | the prune routes | high | mitigate | Both steps are POST forms; the preview and the confirm are separate submits; the confirm form renders only when the preview returned a non-zero count, and the server re-derives the count anyway. |

| T-08-28 | Tampering / Denial of Service | the suspended append-only trigger left down | high | mitigate | The suspension and the re-arm happen inside one transaction that also holds the deletes, so a failure rolls the trigger back with them; an automated assertion reads the database catalog after the commit to prove the trigger is armed again, with a negative control proving the assertion can fail.
