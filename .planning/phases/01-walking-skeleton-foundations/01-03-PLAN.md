<objective>
Build the phase's core vertical slice: a LinkedIn search becomes normalised listing rows in the queue,
and the operator can trigger it from the UI without the page freezing.

Purpose: this is the capability the phase goal names — "a listing scraped from LinkedIn and Indeed
exists in the DB and is browsable in the running app". The adapter port is the project's central
extensibility seam (SRC-04), the total `FetchResult` is what makes a blocked board degrade rather
than abort the run (SRC-05), and `run_pipeline()` is the one callable the Phase 8 scheduler will
reuse (D-22).

The external network call is stubbed at the transport boundary in tests (committed fixtures), which
is exactly the stub that can be filled later without an architectural change: the adapter, the
port, the ingest path, the persistence and the UI are all real code here.

Output: the LinkedIn adapter over the shared JobSpy transport, the pure domain layer, the sanitise
stage, `run_pipeline()`, the run trigger + status poll, and the fixture-driven tests.
</objective>
