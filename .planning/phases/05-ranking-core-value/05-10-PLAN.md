<objective>
Close gap G-05-2: the app never discloses that ranking requires a host-placed CV fact store, nor the exact path it reads, nor how to supply one. `run_ranking` returns silently when the store is absent (rank.py:377-387, D-94) and, because `ranked_count` stays NULL, the queue ranking strip could not render at all before plan 05-08 — so the skip was invisible by construction. A fresh checkout has an empty, gitignored `cv/`, so every user hits it. Compounding it, the operator docs stop at the review draft and never state the promotion to `cv.yaml`, so the documented escape hatch was itself incomplete.

Purpose: the user asked "also where on the page do i provide my own cv? its not clear to me how that works". The CV is a host file by explicit design (D-58: `compose.yml` mounts `./cv:/cv`; `config.py` sets `cv_dir=/cv`; `rank.py` reads `/cv/cv.yaml`), so the correct fix is disclosure and instruction — never intake.

Output: one shared, total `fact_store_report` helper; a CV fact-store card on `/settings` naming the path and the supply steps; an unconditional CV status line on the queue page; a `cv` object in `GET /health` mirroring `tectonic`; and the promotion step documented where the in-app copy points.
</objective>

<scope_decision>
**No CV upload UI — declared, not silently skipped.** `05-UAT.md` records an explicit `out_of_scope` for this gap: an upload is a scope change (a new trust boundary, `python-multipart` is deliberately absent — `app/api/searches.py` and `app/api/events.py` hand-parse urlencoded forms — plus a new route, template and CSRF surface), and no phase in the 8-phase roadmap owns CV intake. The truth asks the app to *tell the user* a fact store is required and *how to supply it*. Every task below is disclosure, instruction or reporting only.

**Choice of `/health` key names.** The report mirrors `_tectonic_report`'s SHAPE and totality — a small async/sync function whose own failure is caught and reported, never raised, and never changing `status` — but its keys are `available`, `path`, `error` rather than `available`, `version`, `error`: a fact store is a data document with no engine version, and the path is the operator's actionable datum. This is stated rather than left implicit because it is the one place this plan departs from a literal reading of the guidance.
</scope_decision>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| operator filesystem → `fact_store_report` → browser | A path and a load outcome outside the repository cross into rendered markup and a JSON body |
| application config → rendered path | The displayed path must be the one the loader reads, or the disclosure is wrong |
| `/health` JSON → any consumer | The body is machine-readable and may be scraped or logged |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-05-43 | Information Disclosure | `fact_store_report` error value → settings card / `/health` | medium | mitigate | The report carries the exception CLASS NAME only; the helper never renders or serialises the message, and an acceptance criterion asserts the exception message appears nowhere in the module. A YAML error's own text can echo document content, so nothing from the exception beyond its type crosses the boundary. |
| T-05-44 | Repudiation | the disclosed path | high | mitigate | The path is computed once from `Settings.cv_dir` + `rank.CV_FILENAME` — the same expression the loader uses — and shared by all three surfaces, so no surface can name a path the app does not read. An acceptance criterion pins the settings card to the configured expression rather than a literal. |
| T-05-45 | Spoofing | the CV status line | medium | mitigate | The line is driven by a real load attempt, not by a file-existence check, so a store that exists but cannot be decoded is reported as "no readable CV fact store" rather than as healthy; the copy deliberately never says "missing", which would be false for the unreadable and non-decodable cases. |
| T-05-46 | Elevation of Privilege | CV intake | high | mitigate | No upload route, form, multipart handling or dependency is added: the truth asks for disclosure, and the CV stays a host file (D-58). This keeps the app's only input boundaries unchanged and adds no CSRF or file-write surface. |
| T-05-47 | Denial of Service | settings / queue / health render paths | low | mitigate | The probe is one small local file read per render, wrapped so it can never raise, and `/health` reports it without affecting `status`, so an absent or corrupt store yields a truthful object rather than a 500 or a degraded app. |
| T-05-SC | Tampering | npm/pip/cargo installs | high | mitigate | This plan installs no package: it edits four existing modules, two templates, three existing test files, one new test file and two documents. `python-multipart` stays deliberately absent. |
