<objective>
Make success criterion 4 structural rather than aspirational: **untrusted content has no channel into
the system prompt, tools are denied by default through the server's documented control, and the deny is
observed on a real call instead of asserted.**

Purpose: PITFALLS m5 and M10 make this the phase's sharpest boundary. Anybody can post a job listing;
the opencode server is a shell-capable agent. Research found that the message-level `tools` field is a
name→boolean map, is deprecated in favour of a session `permission` ruleset, and that a blanket deny
could break the very structured-output path this phase exists to prove — so the deny must be enforced
in a documented place **and** watched.

Output: the permission-ruleset encoding, the session body builder, the trust-boundary guard and its
guard-can-fail companion, the scoped import-discipline guard, and the rendered observation of what the
call actually returned.

**MVP framing — user story (MVP_MODE active):** **As** the local operator feeding untrusted job
listings into a shell-capable agent, **I want** proof that the listing text never became an instruction
and that the agent had no tools to abuse, **so that** I can point this at a real listing corpus without
opening an RCE surface.

**Covers:** success criterion 4 in full; §6.3's trust-boundary table; §6.5's import rule.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| job-listing text (untrusted) → prompt | Instruction-like content must be a recorded finding, never an instruction, and must never reach `system`. |
| model → tool invocation | The opencode server is shell-capable; an injected instruction that reaches a tool is an RCE path. |
| app modules → `httpx`/`subprocess` | A second HTTP path or a process spawn outside `app/llm/` would bypass the port's controls. |
| `GET /experimental/tool/ids` | The tool-name list is explicitly experimental and must not be pinned. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-3-01 | Tampering / Elevation of Privilege | prompt assembly | high | mitigate | The port has no `system`-from-data parameter; `SELFTEST_SYSTEM_PROMPT` is a module constant with no interpolation (asserted in 03-01 Task 3); untrusted content exists only as `parts`; the builder emits text parts only; the response is schema-constrained. Task 1 asserts the `system` value is emitted verbatim with nothing appended. |
| T-3-03 | Elevation of Privilege | tool abuse via injected text (M10) | high | mitigate | Default-deny session `permission` ruleset (the documented control), no message-level `tools` grant by default, a `ValueError` on a wildcard `tools` key, and the parts/`info` observation so a broken deny is a finding. The plan explicitly does not blanket-deny beyond the documented ruleset, because structured output is implemented via an internal tool and over-denying would break the proven path. |
| T-3-18 | Elevation of Privilege | a bypass HTTP path outside `app/llm/` | medium | mitigate | The scoped import guard fails if `httpx` appears under `app/pipeline`, `app/api`, `app/web`, `app/domain` or `app/probe`; `subprocess` is asserted absent everywhere outside `app/llm/`; `app/sources` is excluded with a written rationale, not silently. |
| T-3-19 | Information Disclosure | the observation recording parts | medium | mitigate | Only part **type names** and `info` **key names** are recorded; a sentinel-in-text test proves no part text reaches the page, the log, or the `llm_calls` row. |
| T-3-20 | Tampering | an experimental surface pinned by accident | low | mitigate | `GET /experimental/tool/ids` is deliberately not pinned and not called; the deny uses a documented `permission` ruleset rather than a discovered tool-name list. |
| T-3-SC | Tampering | package installs | low | accept | Zero new packages; this plan edits source, tests and templates only. |
</threat_model>
