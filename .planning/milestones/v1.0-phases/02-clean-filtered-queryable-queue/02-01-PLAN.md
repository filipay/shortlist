# Plan 02-01 — Schema spine: migration 0002, the guard churn, and the settings envelope

**As a** job-seeker running the pipeline, **I want to** store named filter rules, a last-visit watermark, and a run's reason against a schema that is honestly tested, **so that** every later capability in this phase has somewhere real to live and the schema contract cannot silently drift.

<objective>
Add the one small additive migration this phase needs and pay its four guard costs in the same breath, so a correct implementation never reads as a regression.

Purpose: Phase 1 deliberately shipped migration 0001 with every Phase-2 table *except* four things: `filter_rules`, the last-visit watermark, the run-reason/criteria-snapshot columns, and the `listing_dupes` uniqueness/an audit index — 0001 already carries the rest of the Phase-2 scaffolding (`listing_dupes.snapshot_json`/`reverted_at`, `listing_exclusions`, append-only `listing_events`, `searches.version`, the `runs` counters, `listings.blocking_key`, and `listing_fts` with its triggers), while none of the Phase-2 behaviour, repositories, routes, settings or templates exists yet (D-47). Output: `alembic/versions/0002_*.py`, `app/db/models.py` mirroring it, an ORM-drift guard, four updated guards, and the four new `Settings` knobs.
