# Plan 02-08 — Criteria you can tune from the UI: named searches, typed rule forms, and honest capability warnings

**As a** job-seeker whose priorities shift week to week, **I want to** edit my saved searches and their exclusion rules in the browser, and be told when a board cannot honour one of them, **so that** I can retune the queue without touching code and without believing a filter that never applied.

<objective>
Deliver the criteria CRUD surface: named searches with their own rules, enable/disable, edit, delete, a per-kind rule form, the pre-run capability report, and a per-search run action.

Purpose: this is CRIT-01, CRIT-03 and FILT-04, and success criterion 3 of the phase. Plans 02-03 and 02-05 built the pure criteria/rule decision layer and made the pipeline consume it; this plan is the surface that writes it — which is what makes FILT-04 ("tune filter rules from the UI without a code change") true rather than aspirational.

Output: the write half of `search_repo.py`, `app/api/searches.py` with the CRUD + toggle + run-one routes, `criteria.html`, single-search scoping in `run_pipeline`, and four test modules.
</objective>

### Decisions this plan implements

- **D-32** — one unified named search carries both the fetch query and its own exclusion rules; enabling it adds it to the run and the queue unions all enabled searches, with scope-to-one supported. Reuses `searches.criteria_json`, `searches.enabled`, `searches.is_default`. *(Reversibility: costly — splitting later into "searches fetch, one global filter set" would re-home every rule and rework both the criteria and the queue UI.)*
- **D-34** — the UI renders a purpose-built **form per kind**; no raw JSON editor, and **no Jinja in any logic position** (rendering conditionals are fine; computing filter semantics in a template is banned).
- **D-33** — `searches.version` is bumped on edit; a run stores its own snapshot, so no version-history table and no diff/rollback UI exist in v1.
- **D-37 (carried SRC-09)** — the criteria compiler consumes each adapter's declared capabilities so an unsupported filter is **reported, not silently ignored**. `compile_query_for_source()` + `CapabilityWarning` already ship and are unconsumed before this phase.
- **D-45** — "Run search now" runs every enabled search; the criteria page additionally offers a per-search "Run this one" action for iterating on a single query. No picker dialog on the main trigger.
- **D-36** — retuning a rule can bring a previously-excluded listing back, with no deletion needed; this plan's edits only change future runs.
- **D-46** — Jinja + HTMX + Alpine, vendored assets, no CDN.

### The six rule kinds and their parameter shapes (from plan 02-03's contract)

| Kind | Form fields | Notes |
|------|-------------|-------|
| `salary_floor` | amount (integer), currency (default `EUR`), interval (default `year`) | help text must state that a listing with **no** salary is not excluded |
| `exclude_keyword` | terms (a comma- or newline-separated list), fields (checkboxes over `title`, `description`) | help text must state that a match anywhere in a listed field excludes the listing |
| `location` | allow (a list of location terms), mode (default `substring`) | help text must state that an unknown location is not excluded |
| `remote` | require (a checkbox, default on) | help text must state that an unknown remote flag is not excluded |
| `seniority` | allow (a list), deny (a list), unknown_passes (a checkbox, default on) | help text must state that an unknown seniority is not excluded |
| `company_blocklist` | companies (a list), match (default `norm_equals`) | — |

The **unknown-passes** semantics are the resolved A2/A3 user decision and **must appear in the form's help text**, because the policy is invisible otherwise.

### Not a violation of "no Jinja in any logic position"

`{% if %}`, `{% for %}` and `{{ value }}` are rendering and are expected. What D-34 bans is a template **evaluating filter semantics** — for example a template deciding whether a listing passes a rule, or computing an annualised salary. The form's field visibility for the active kind comes from Alpine `x-data`/`x-show` over a server-supplied kind string, or from server-rendered per-kind blocks.

## Flagged Assumptions (edge-probe coverage)

The phase's edge-coverage report left 28 rows `unresolved`. Those owned by this plan:

- **[CRIT-01 · idempotency]** What happens if a create is submitted twice? **Assumption:** there is **no** uniqueness constraint on `searches.name` (none exists in the schema, and adding one now would be a migration this phase does not need), so a double submit creates two searches. The control is the form's post/redirect/redirect idiom: a successful create returns the refreshed list fragment rather than accepting a second submit of the same form state, and a test asserts two identical POSTs produce two searches *and* that the second is distinguishable — recorded honestly rather than claimed as idempotent. A future unique constraint is additive.
- **[CRIT-01 · concurrency]** Two browser tabs editing the same search. **Assumption:** last write wins; `version` is incremented by each accepted write, so the version records that two writes happened even though neither caller was rejected. This is deliberate and matches D-33's "no diff/rollback UI in v1". A test asserts two sequential edits give `version == 3` after a create. Optimistic concurrency (the `_verify_original_matches` pattern in the Phase-6 research) is the upgrade path and is out of scope here.
- **[CRIT-03 · unclassified — review manually]** Surfaced, not dropped. **Assumption:** "disable" is a write to `searches.enabled` that changes **no** other field and therefore does **not** bump `version` — disabling is not a criteria change, and bumping the version on a toggle would make the version meaningless. Asserted: toggling leaves `version` unchanged; editing a rule bumps it. Consequently a run's snapshot records the criteria but the enabled/disabled state at run time is recorded by which searches contributed rules, so the snapshot is taken from the **enabled** set.
- **[FILT-04 · unclassified — review manually]** Surfaced, not dropped. **Assumption:** "tune filter rules from the UI without a code change" is satisfied for the six kinds and their documented parameters, and **not** for adding a new kind — adding a kind requires the migration CHECK, `RULE_KINDS`, the evaluator and the form, by design (the safety of a typed row over a free-form expression). Stated in the module docstring so the boundary is a decision, not a gap.
- **[FILT-04 · boundary / precision on the salary floor field]** The form accepts an integer amount. **Assumption:** the value is validated as a non-negative integer server-side before persist; a fractional or negative amount is rejected with a rendered error and no row is written. The annualisation contract stays in `app/domain` (plan 02-03) and is not duplicated in the UI. Asserted for a negative, a fractional and a non-numeric value.

### Not in this plan

No queue changes (plan 02-07), no save/hide events (plan 02-09), no run history page (plan 02-10), no criteria version-history table or diff/rollback (deferred by D-33), and no change to the six rule kinds or the unknown-passes policy (both are plan 02-03's).

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| the criteria form (user-supplied) → `searches` and `filter_rules` | free-text names, terms and numeric parameters are persisted and later trusted by the pipeline's evaluators |
| adapter capabilities → the user's belief about their filters | a filter a board cannot honour, reported nowhere, makes the user believe a rule applied |
| the criteria page → the browser | search names and rule terms are user text rendered back into markup |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-31 | Tampering | rule parameters written from the UI | high | mitigate | `validate_rule_params` rejects per kind before any insert (a non-integer/negative/non-numeric `salary_floor.amount`, empty term lists, an unrecognised `fields` entry, an unknown `kind`); there is no raw JSON editor, so the shape is constrained by the form; the database additionally enforces the kind vocabulary with the named `ck_filter_rules_kind` CHECK from plan 02-01; plan 02-03's evaluators degrade gracefully if a bad row ever appears. |
| T-02-32 | Repudiation | silent capability drop (D-37 / SRC-09) | high | mitigate | Every enabled search is compiled against every enabled adapter's declared capabilities at render time and the resulting `CapabilityWarning` objects are shown with the board, the filter and the reason, plus the local-enforcement statement; the registry walk is wrapped so it degrades to no warnings rather than a 500. |
| T-02-33 | Tampering | version churn making `searches.version` meaningless | medium | mitigate | `version` is bumped only when a stored field actually changes; a whole-search enable/disable deliberately does not bump it; both behaviours are asserted, so a run's snapshot number stays a meaningful reference. |
| T-02-34 | Tampering (destructive delete) | `delete_search` | medium | mitigate | Delete removes the search and its rules only, in one transaction; listings, exclusions, merges and runs are untouched (asserted by count comparison); a completed run keeps its criteria snapshot, so reproducibility survives the delete. |
| T-02-35 | Tampering (XSS) | search names and rule terms rendered back | high | mitigate | Jinja autoescape with no `|safe`; names pass through `sanitize_short_field` and terms through `sanitize_text` at the boundary; a test seeds a name containing an HTML tag and asserts the escaped form appears and the raw tag does not. |

Residual risk accepted: a double-submitted create form produces two identically-named searches, because there is no unique constraint on `searches.name`. This is recorded as an explicit flagged assumption; the form's fragment response makes an accidental double submit unlikely, and adding a unique constraint later is additive.
