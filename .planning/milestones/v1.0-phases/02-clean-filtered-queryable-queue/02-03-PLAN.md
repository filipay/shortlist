# Plan 02-03 — The pure decision layer: filter rules, criteria assembly, and the injection catalogue

**As a** job-seeker, **I want to** have my exclusion rules evaluated by small deterministic functions I can reason about and test in isolation, **so that** a rejection is explainable, a bad rule cannot empty my queue, and the reason is decided by code rather than by a template.

<objective>
Build the three pure modules the rest of the phase leans on: the six filter-rule evaluators, the criteria-to-query assembler, and the Phase-1-deferred injection pattern catalogue (D-38 — an `_INJECTION_PATTERNS`-style rule set pattern-copied from Resume-Matcher's `improver.py` and attributed per Apache-2.0 §4).

Purpose: `app.domain.*` may import no I/O (the AST guard in `tests/test_import_discipline.py` forbids `httpx`, `sqlalchemy`, `jobspy`, `jinja2`, `subprocess`, `fastapi`). Everything that *decides* therefore lives here as a total function over frozen dataclasses, and everything that *writes* stays in a repository. This is what makes FILT-02 ("every rejection records which rule fired and why") cheap: the pure function produces the evidence, the repository persists it verbatim.

Output: `app/domain/filter.py`, `app/domain/criteria.py`, an extension to `app/domain/sanitize.py`, and three unit-test modules.
</objective>

### Decisions this plan implements

- **D-34** — filter rules are typed rows with six kinds (`salary_floor`, `exclude_keyword`, `location`, `remote`, `seniority`, `company_blocklist`); evaluators are **pure functions in `app.domain`** and the UI renders a purpose-built form per kind (the form is plan 02-08). *(Reversibility: costly — the kind vocabulary is mirrored by the named `ck_filter_rules_kind` CHECK added in plan 02-01, so widening it later is a coordinated migration plus a UI change.)*
- **D-32** — one unified named search carries both the fetch query and its own exclusion rules; the queue unions all enabled searches. *(Reversibility: costly — splitting later into "searches fetch, one global filter set" would re-home every rule and rework the criteria and queue UI.)*
- **D-36** — rules are re-evaluated from scratch every run; exclusions are per-run observations, not blacklist state. This is why `evaluate()` is stateless and returns a fresh outcome list.
- **D-38** — extend `app/domain/sanitize.py` with an `_INJECTION_PATTERNS`-style rule set, pattern-copied from Resume-Matcher's `improver.py` and **attributed per Apache-2.0 §4**.
- **Resolved user decision (A2/A3)** — **do not exclude unknowns.** `salary_floor`, `remote`, `seniority` and `location` rules reject only on a *present, contradicting* value. Rationale: JobSpy's salary extraction is `Country.USA`-only, so excluding unknowns would empty most of an Irish corpus.
- **Resolved user decision (A4)** — multi-search rule scope is the **UNION** of every enabled search's rules; a rejection by any enabled search's rule removes the listing. Document this in the module docstring and in the criteria UI copy (the copy is plan 02-08).
- **D-24 / D-46** — `app.domain.*` imports no I/O; `Settings`, never constants.

### Module contracts to satisfy

`app/domain/filter.py` — frozen dataclasses `RuleSpec` (`rule_id`, `kind`, `params`, `position`), `ListingFacts` (`title`, `title_norm`, `description`, `company_norm`, `location_norm`, `remote_flag`, `seniority`, `salary_min`, `salary_max`, `salary_interval`), `RuleOutcome` (`excluded`, `rule_id`, `rule_kind`, `detail`), and a total `evaluate(rules, facts) -> list[RuleOutcome]` returning only the excluding outcomes.

Per-kind semantics (each `detail` mapping is the FILT-02 "why"):

| Kind | `params` | Excludes when | `detail` keys |
|------|----------|---------------|---------------|
| `salary_floor` | `amount`, `currency`, `interval` | a salary figure is **known** and its annualised value is below the floor | `floor`, `salary_min`, `salary_max`, `interval`, `currency` |
| `exclude_keyword` | `terms`, `fields` | any term is a casefolded substring of one of the listed fields | `term`, `field`, `count` |
| `location` | `allow`, `mode` | `location_norm` is **non-null** and matches none of the allowed terms | `location_norm`, `allowed` |
| `remote` | `require` | `remote_flag` is exactly `False` | `remote_flag`, `require` |
| `seniority` | `allow`, `deny`, `unknown_passes` | a deny token matches, or `seniority` is non-null and matches no allow token | `seniority`, `allow` |
| `company_blocklist` | `companies`, `match` | `company_norm` equals (or token-matches) an entry | `company_norm`, `matched` |

`detail` values are terms, field names, counts and numbers. A `description` field name may appear as a *key value* in `exclude_keyword.detail.field`; the description **text** never appears.

`app/domain/criteria.py` — pure assemblers: `search_query_from(criteria)` producing a `SearchQuery`, and `rule_specs_from(rows)` mapping raw mappings into an ordered `list[RuleSpec]`.

## Flagged Assumptions (edge-probe coverage)

The phase's edge-coverage report left 28 rows `unresolved`. Those owned by this plan:

- **[CRIT-01 · idempotency]** Unresolved at the requirement level. This plan's slice is the pure assembler: `search_query_from(criteria)` is a pure function, so calling it twice on equal input returns equal output, and `rule_specs_from` is stable-ordered. **Assumption:** idempotency of *writes* is not asserted here — it belongs to plan 02-08's CRUD routes and to the `(search_id, position)` ordering contract.
- **[CRIT-01 · concurrency]** Unresolved. **Assumption:** the pure layer is racing-immune because it holds no state; the concurrent-write contract is plan 02-08's (a last-write-wins update plus a deliberate `searches.version` bump, not a compare-and-swap).
- **[FILT-01 · unclassified — review manually]** Surfaced, not dropped. **Assumption:** "deterministic rules reject listings before any LLM call" is satisfied structurally in this plan (the evaluators are pure and total) and *observationally* in plan 02-05 (the filter stage writes `listing_exclusions` from a run that makes no LLM call). No LLM client is imported anywhere in this plan; `app/llm` must not appear in any of the three new modules.
- **[FILT-02 · adjacency]** When two rules both fire, do they merge, collide, or separate? **Assumption:** they **separate** — one outcome per firing rule, never merged. This is what makes the per-rule counts in plan 02-05 (`GROUP BY rule_id`) correct, and it is asserted in `tests/domain/test_filter.py`.
- **[FILT-02 · empty]** Result for an empty rule set, an empty field, or a `None` field. **Assumption:** an empty or absent rule set yields `[]` (no exclusion); an empty/absent `location_norm` never trips the `location` rule; an empty `terms` list never trips `exclude_keyword`. All three asserted.
- **[FILT-02 · ordering]** When rules compare equal, is the output order specified and stable? **Assumption:** outcomes are ordered by `(position, rule_id)`; a tie on `position` is broken by the string `rule_id`, which is unique, so the order is total and stable across runs. Asserted.
- **[FILT-01 / FILT-02 · boundary and precision]** `salary_floor` at exactly the floor, one euro below, and one euro above. **Assumption:** the comparison is strictly below the floor (`annualised < floor` excludes), so a listing whose annualised salary equals the floor **passes**. Asserted at all three points, including an annualised value derived across intervals so the rounding contract is pinned: `annualise_salary` is used verbatim, no second rounding is applied, and the comparison is on the annualised float.
