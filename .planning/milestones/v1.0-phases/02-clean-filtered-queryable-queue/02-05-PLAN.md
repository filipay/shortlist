# Plan 02-05 — Deterministic hard filtering, criteria snapshots, and the run's reason

**As a** job-seeker who pays for LLM calls and reads a short queue, **I want to** have deterministic rules reject the wrong listings before any model call and record exactly what fired, **so that** my spend goes only to plausible jobs and I can always answer "why is this not in my queue?".

<objective>
Make a run filter deterministically and explain itself: load the enabled searches' rules, evaluate them against the persisted listings, write one exclusion row per firing rule, snapshot the criteria onto the run, and persist a structured reason for a thin or empty queue.

Purpose: this is FILT-01/02, CRIT-02 and RUN-03, and it is success criteria 2 and 5 of the phase. The ordering is fixed by `ARCHITECTURE.md` §8.1: fetch fully → sanitise → normalise → **dedup/merge** → **hard-rule filter** → cap. Filtering before merging would discard the copy that carried the salary, so the filter stage is inserted **after** the dedup stage written in plan 02-04.

Output: `app/db/repositories/search_repo.py` and `exclusion_repo.py` (the read/write side), `app/pipeline/filter_stage.py`, `app/domain/run_reason.py`, the stage insertion and counter writes in `run_pipeline()`, and five test modules.
</objective>

### Decisions this plan implements

- **D-34** — rules are typed rows; every rejection writes `listing_exclusions(rule_id, rule_kind, detail_json, run_id)`.
- **D-36** — rules are re-evaluated from scratch every run; one exclusion row per listing+run+rule, append-only, never updated. Retuning a rule can bring a listing back with no deletion.
- **D-37 (carried SRC-09)** — the criteria compiler consumes each adapter's declared capabilities so an unsupported filter is **reported, not silently ignored**. `compile_query_for_source()` and `CapabilityWarning` already ship and are unconsumed; this plan is their first real consumer.
- **D-33** — past-run reproducibility is a criteria snapshot on the run plus a `criteria_version` on each exclusion row. No version-history table.
- **D-44** — a thin or empty queue is explained by a persisted structured reason + counts + a rendered sentence, plus a collapsible raw stage log. Computed deterministically, with no LLM.
- **D-45 / A6 (research assumption)** — **one `runs` row per trigger**, with per-search sections inside `criteria_snapshot_json` and `reason_counts_json`. The per-search row shape would break the existing "one trigger = one `runs` row" contract in `tests/api/test_run_trigger.py`, so the sectioned shape is chosen and documented.
- **Resolved user decisions A2/A3 and A4** — unknowns are never rejected; the rule scope is the union of enabled searches.

### The run-reason precedence order (fixed here, deterministic)

```
1 no_sources_enabled : adapters resolved == 0
2 all_sources_failed : adapters resolved > 0 and every source status != 'ok'
3 zero_fetched       : every source status == 'ok' and total fetched == 0
4 all_filtered       : fetched > 0 and excluded_by_rule > 0 and survivors == 0
5 nothing_new        : survivors > 0 and every survivor predates the watermark
6 mixed              : anything else (two or more causes co-occur)
```

The first matching cause wins. The order is the contract; it is asserted branch by branch.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| criteria + rule params (user-supplied) → evaluated against listings | rule params are attacker-influenceable if a criteria import path is ever added; the evaluators must treat them as data |
| run → persisted exclusion + reason rows | a skipped or unapplied rule that is not recorded is a silent lie about what happened |
| board capabilities → the user's belief about their filters | a filter a board cannot honour, recorded nowhere, would make the user believe a rule was applied |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-16 | Tampering | rules loaded from the database and evaluated | medium | mitigate | Rules pass through plan 02-03's pure `evaluate`; the ORM row never reaches the pure layer; all SQL is bound-parameter; rules are ordered `(search_id, position, rule_id)` so the evaluation order is deterministic; `kind` is constrained by the plan-02-01 CHECK. |
| T-02-17 | Information Disclosure | `listing_exclusions.detail_json`, `runs.stage_log_json`, `runs.reason_counts_json`, `runs.errors_json` | high | mitigate | `detail_json` carries the matched term, the field name and a count — never the field's text; the stage log carries stage names, counts and board/filter names; the capability warning text is `source` + `filter_name` + `reason`; a test asserts the description text does not appear in an exclusion's detail. No credential is read or written anywhere on this path. |
| T-02-18 | Denial of Service (self) | one malformed rule emptying the queue or aborting the run | high | mitigate | `evaluate` is total (unknown kind, non-mapping params, wrong-typed value → skipped); the stage catches per-listing failures, counts them and continues; a skipped rule is counted so it is visible rather than assumed applied; the stage log is bounded so a pathological run cannot write an unbounded blob. |
| T-02-19 | Repudiation | a capability drop recorded nowhere (D-37 / SRC-09) | high | mitigate | `_fetch_one`'s existing warnings are extended, not replaced: they stay in `runs.errors_json` with the existing shape and additionally land in `runs.stage_log_json` under `criteria_compile` as structured triples; the risk is further reduced because the same rules are enforced locally after the fetch, so the warning reads "enforced locally" rather than "not applied". |
| T-02-20 | Tampering | a criteria edit retroactively rewriting what a completed run claims it used | medium | mitigate | The snapshot is written before the fetch and never rewritten in `_finish`; a test edits the criteria after a run and asserts the stored snapshot is unchanged. |

Residual risk accepted: the filter is deterministic but only as good as the user's rules; a mis-typed `exclude_keyword` term can remove a whole class of listings. Mitigations are D-36's append-only per-run observations (retuning a rule brings listings back with no deletion), the per-rule counts surfaced in plan 02-07's excluded toggle, and the run reason distinguishing `all_filtered` from every other empty-queue cause.
