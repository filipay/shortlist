# Plan 02-06 — The merge audit trail: see the rate, inspect the rows, undo a bad merge

**As a** job-seeker who does not trust an automatic merge I did not see, **I want to** look at the merges the pipeline made and undo one that combined two different jobs, **so that** automatic deduplication is safe to leave switched on.

<objective>
Deliver the merge rate, the rows behind it, and one-click revert.

Purpose: this is QUEUE-04 and QUEUE-09, and the second half of success criterion 1. Plan 02-04 merged automatically and retained the evidence; this plan makes that evidence visible and the merge undoable. The design point that makes the undo cheap is that a merge never moved or deleted anything: the twin is still an ordinary `listings` row, its `listing_sources` rows still point at it (the A5 divergence), and `snapshot_json` holds the survivor's pre-merge values. Revert is therefore a flag flip plus a field restore — not a data migration.

Output: `dupe_repo.revert_merge` / `list_merges` / `merge_rate` / `merge_summary_for_listings`, a `GET /merges` page with a `POST /merges/{id}/revert` action, `merges.html`, and two test modules.
</objective>

### Decisions this plan implements

- **D-29** — a dedicated Merges audit view plus a merge-rate statistic, with one-click revert. This satisfies QUEUE-09 directly ("see the merge rate and the rows behind it") and gives revert a home. *(Reversibility: reversible.)*
- **D-26** — the merged twin's record is retained and must be human-inspectable. This plan is where that becomes true in-phase: each Merges row shows the twin's own source, URL, title, company and location alongside the survivor's, and the survivor's snapshot values, so the user can judge whether the merge was right. (The Phase-5 job-detail page will later carry the same data per listing; inventing that page here would be out of scope for a phase with no detail view.)
- **D-28** — revert is a **full undo plus negative memory**: restore the survivor's snapshot fields, mark `reverted_at` and `reverted_by`, and record the pair as deliberately distinct so the next run does not silently re-merge it.
- **D-25** — merging is automatic, so the negative memory is a load-bearing **pre-check** on the merge path (implemented in plan 02-04); this plan supplies the revert half.
- **D-36** — reverting is not a counter-operation on a run; exclusions and merges are per-run observations. Reverting marks the audit row; a later run simply declines to re-merge.
- **D-43** — the runs page and its last-run strip are plan 02-10; this plan's page is the Merges view only.

### Visibility model (state it, do not re-invent it)

An absorbed twin is excluded from the queue because it has a `listing_dupes` row with `reverted_at IS NULL` — **not** because of a `hide` event. Consequences:
- revert needs no `unhide` event; the twin reappears the moment `reverted_at` is set;
- this plan writes **no** `listing_events` row on merge or on revert. `listing_events` records *user* actions (save/hide/unsave/unhide/view); a merge is a system action already recorded in `listing_dupes`, and writing a synthetic `hide` would make the event log claim a user action that never happened and would require an `unhide` on every revert.

## Flagged Assumptions (edge-probe coverage)

The phase's edge-coverage report left 28 rows `unresolved`. Those owned by this plan:

- **[QUEUE-04 · adjacency]** What happens when two merges touch the same listing? Plan 02-04 allows a chain (A survives; B and C each absorbed onto A), and each merge wrote its own snapshot. **Assumption:** `revert_merge` restores **every field named in that row's snapshot**, unconditionally, and the UI presents merges **newest-first** so reverting a chain top-down is the natural order. A revert applied out of order can drop a later merge's fill; that is recoverable by reverting the later merge too, and the test covers the newest-first order. This is documented in `revert_merge`'s docstring rather than left implicit.
- **[QUEUE-04 · empty]** What does revert do when the snapshot is empty, absent, or names a field that no longer exists? **Assumption:** an absent or empty `snapshot_json` is a no-op restore (the audit flag is still set, so the pair is still separated); a snapshot key that is not a column on `listings` is skipped and counted in the returned result rather than raising. Asserted.
- **[QUEUE-04 · ordering]** When two merges compare equal, is output order specified? **Assumption:** `list_merges` orders by `(merged_at DESC, id DESC)` — newest first, with the unique `id` as the mandatory tie-break (equal `merged_at` values are common when one run merges several pairs in the same second). Asserted by merging two pairs in one run and checking the order is stable across two reads.
- **[QUEUE-09 · boundary]** The merge-rate denominator at the edges: zero fetched, and `deduped_count` greater than zero with zero fetched. **Assumption:** the rate is `None` (rendered as an em dash), not `0.0`, when `fetched_count` is zero or null — a division by zero is a bug and a `0%` reading would be a lie. Asserted at zero and at one.
- **[QUEUE-09 · adjacency]** Does the rate count a reverted merge? **Assumption:** the rate counts **un-reverted** merges only, so reverting a merge moves the number; the page additionally shows the reverted count so the difference is visible. Asserted.
- **[QUEUE-09 · empty]** The rate with no merges at all. **Assumption:** `0.0` with a non-zero denominator and the explicit "no merges recorded" copy; with a zero denominator it is `None`. Asserted.
- **[QUEUE-09 · ordering]** Which window does the rate cover? **Assumption:** the rate is computed over the **latest run** (the same run the queue's last-run strip names) and the page states that window in the heading, so the number is never an unlabelled all-time aggregate. Asserted by driving two runs and checking the rate reads the latest.
- **[QUEUE-09 · precision]** Where can rounding or tie-breaking bite? **Assumption:** the rate is stored and rendered as a rounded percentage **for display only**; the underlying values are the two integers (`deduped_count`, `fetched_count`), which are rendered beside it. No float is persisted. Asserted by checking the page contains both integers and that the computed display value for a known pair matches (`1/3` renders `33%`).

### Not in this plan
