# Plan 02-09 — Save and hide, recorded as append-only events

**As a** job-seeker triaging a queue, **I want to** star the jobs worth another look and hide the ones I never want to see again, with both actions reversible, **so that** the queue gets sharper every morning without me losing the record of what I did.

<objective>
Add the two queue signals the phase promises — Save and Hide as **distinct** actions (D-41) — written as append-only `listing_events` with the current state projected from the latest event, and surfaced as the `Hidden` and `Saved` queue filters.

Purpose: this is QUEUE-08 and success criterion 4 of the phase. Phase 1 already ships the `listing_events` table, its event-type CHECK and its append-only triggers — but nothing writes to it. This plan adds the write route, the projection query and the row controls. The design constraint is the project's established pattern: current state is **projected from the latest event**, never stored in a mutable column, so the history is complete and a wrong click is undone by appending another event rather than by editing one.

Output: `app/db/repositories/event_repo.py`, `app/api/events.py`, the router registration, the row controls in `_listing_row.html`, and two test modules.
</objective>

### Decisions this plan implements

- **D-41** — Save and Hide are **distinct** actions written as append-only `listing_events` (event types already exist: `save`, `unsave`, `hide`, `unhide`, `shortlist`, `view`) with the current state projected from the latest event. Hidden listings leave the default queue and are reachable via a `Hidden` filter with one-tap undo; saved listings get a `Saved` filter and a star. The Phase-1 append-only triggers are reused unchanged.
- **D-36** — exclusions and merges are per-run observations; a save or hide is a durable user action. The two are different kinds of record and are not merged into one table.
- **D-46** — Jinja + HTMX + Alpine, vendored assets, no CDN.

## Flagged Assumptions (edge-probe coverage)

The phase's edge-coverage report left 28 rows `unresolved`. Those owned by this plan:

- **[QUEUE-08 · idempotency]** What happens if the same event is posted twice (a double click, or a retried request)? **Assumption:** every accepted POST appends a row — `save` twice produces two `save` rows — and the monotonic projection makes the second a no-op in effect, because "saved" projected from the latest event is still "saved". This is deliberate: deduplicating events would require the application to decide an event is redundant, and the append-only log's value is that it records what actually happened. A test asserts `save` twice leaves the projected state `saved` with two rows, and that `save` then `unsave` leaves `unsaved`.
- **[QUEUE-08 · concurrency]** Two tabs clicking save and hide at the same time. **Assumption:** last event by `(occurred_at, id)` wins, and `id` is the tie-break — two events in the same second (common) are ordered by their insertion id, so the projection is deterministic. The events are not conflicting records; both are true, and the projection picks the most recent. Asserted by inserting two events with an identical `occurred_at` and checking the projection follows the higher `id`.
- **[QUEUE-08 · boundary]** A listing with **no** events at all. **Assumption:** the projection returns an explicit "no state" result (`saved=False`, `hidden=False`, `shortlisted=False`, `last_viewed_at=None`), not a missing key, so a caller cannot mistake an absent listing for an unreadable one. `Hidden`/`Saved` filters therefore treat a no-event listing as visible and unsaved. Asserted.
- **[QUEUE-08 · ordering]** When several events exist, which is "current"? **Assumption:** the latest by `(occurred_at, id)`; `view` events are recorded but do **not** affect the hidden/saved projection, so a `view` after a `hide` does not un-hide. Asserted explicitly — this is the least obvious rule in the projection and would otherwise be an invisible bug.
- **[QUEUE-08 · empty]** The entity absent, or an empty id list. **Assumption:** `state_for_listings([])` returns an empty mapping without issuing a query; a POST for a non-existent listing id returns 404 and appends nothing (there is a real FK, so an insert would raise anyway — the route must reject before the write so the response is a 404 rather than a 500). Asserted.

### Not in this plan

No application-tracker semantics (Phase 7) — a save is a queue signal, not an application stage. No event retention or pruning policy (a Phase-8 ops item). No `shortlist` or `view` UI in this phase; both remain available in the vocabulary, and `shortlist` is deliberately left unwired because Phase 7 owns application stages.
