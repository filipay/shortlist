# Phase 07.1: Code Review Report

**Reviewed:** 2026-10-13T15:41:25Z
**Depth:** standard
**Files Reviewed:** 29
**Status:** issues_found

## Summary

Phase 07.1 retargets the opencode LLM backend from a dead V1 contract to the V2
`/api/*` surface while retaining V1 behind runtime surface detection. The overall
shape is sound: `app/llm/detection.py` refuses to classify from a bare 200 (the SPA
fallback is a real, tested false positive), the V2 generate arm keeps the accepted
"schema rides in the prompt, validation is client-side" design, `TOLERATED_SCHEMA_ERRORS`
/ `_salvage` are byte-identical (verified by diff), the module still contains no
`"/provider"` literal, and the sentinel-redaction boundary is preserved and tested.
The full default suite passes (1754 passed, 2 xfailed) and the V2 request shapes match
`to_v2_session_body`/`to_generate_body` correctly.

The most significant defect is a **behavioral regression on the shipped surface**:
`OPENCODE_MAX_RETRIES` — the documented transport-retry budget that every caller passes —
is completely inert on the V2 arm, so a single transient connect error fails the call
(where V1 would resend), and `attempts` is misreported as `0`. Two secondary issues are a
JSON extractor that can return a prose brace block instead of the payload, and an
unnecessary hard dependency on `/api/provider` that can take discovery (and thus every
completion) down for a payload the parser never reads. One stated documentation condition
(the README half of the accepted prompt-injection residual) is unmet.

The known accepted residual (V2 has no `system` field) is confirmed documented in
AGENTS.md and the runbook and is **not** counted as a finding; the V2 permission/tool
opt-out is a recorded deliberate coverage decision, not a regression.

## Critical Issues

### CR-01: V2 completion path has no transport-retry loop — `OPENCODE_MAX_RETRIES` is inert and `attempts` is misreported

**File:** `app/llm/opencode_server.py:578-606` (dispatch) and `app/llm/opencode_server.py:745-885` (`_complete_v2`)

**Issue:** `complete_structured` computes the transport budget
(`budget = retries or settings.opencode_max_retries`, line 578) but only the **V1** arm
consumes it; `_complete_v2` never wraps its `client.post` calls in a transport-retry loop.
A `httpx.ConnectError`/`TimeoutException` during `/api/session` or `/generate` propagates
straight to the outer total-function envelope, which returns a single failure with
`attempts = 0` — even though a request **was** issued.

Verified by reproduction (`OPENCODE_MAX_RETRIES = 2`, all POSTs raise `httpx.ConnectError`):

```
status error  error_kind unreachable  attempts 0
POSTs issued: ['/api/session']      # exactly one, no resend
```

The V1 arm with an identical failure issues `budget` message POSTs
(`tests/llm/test_complete_structured.py::test_the_client_loop_is_bounded_by_the_retries_argument`
proves 3 requests for `retries=3`). So this is an asymmetry, not a design choice:
on the **installed** surface, the configured retry budget silently does nothing and
every consuming route (`rank`, `tailor`, `draft`, `llm_extract`, `/settings/llm-test`)
has a false expectation of resilience.

This also contradicts the code's own prose, which the phase's binding convention
("no false guarantees in prose") forbids:

* `app/llm/opencode_server.py:537-540` — "**both surfaces resend on a transport failure
  or timeout**, bounded by the `retries` argument … the adapter then applies
  `settings.opencode_max_retries`".
* `app/llm/base.py:135-141` — "When omitted the **adapter applies
  `Settings.opencode_max_retries`**".
* `app/config.py:76-79` — "How many times the client resends a completion that failed at
  the transport layer."

Note the phase partially fixed this class of false statement already: `07.1-06-SUMMARY.md`
records repairing the `.env.example` `OPENCODE_MAX_RETRIES` comment, but the two code
docstrings and the config comment still assert a V2 behavior that does not exist.

**Fix:** Wrap the V2 session POST and each generate POST in the same transport loop the V1
arm uses (retry only on `httpx.TimeoutException`/`httpx.TransportError`, bounded by
`budget`, incrementing `issued`), or — if retrying V2 `generate` is genuinely undesirable —
correct all three prose sites and document that `OPENCODE_MAX_RETRIES` is V1-only. If the
loop is added, `attempts` must report the issued count rather than `0`.

```python
for _attempt in range(1, budget + 1):
    try:
        response = await client.post(url, json=to_generate_body(prompt))
    except httpx.TimeoutException as exc:
        issued += 1
        last_failure = _failure(...)   # timeout vs unreachable, as in the V1 arm
        continue
    except httpx.TransportError as exc:
        issued += 1
        last_failure = _failure(...)
        continue
    issued += 1
    # ... classify and return
```

## Warnings

### WR-01: `_extract_json` returns a balanced prose brace block instead of the JSON object

**File:** `app/llm/opencode_server.py:990-1023`

**Issue:** The extractor takes the span from the **first** `{` to its matching `}` with
brace-depth tracking. A leading sentence that contains its own balanced brace pair makes it
return that prose block and discard the real JSON object that follows — a valid model
response is then classified `invalid` and the schema-retry budget is burned re-issuing a
prompt the extractor will keep mis-reading. Reproduced directly:

```
'use {x} then {"a":1}'                    -> '{x}'
'The set {a, b} is not JSON. Here: {"a": 1}' -> '{a, b}'
'{"a":1}'                                 -> '{"a":1}'   # fine
```

The module docstring claims "the outermost `{…}` block" and
`tests/llm/test_json_extraction.py` only exercises prose **without** braces, so the guard
passes while the failure mode is unobserved (a class the phase's own testing convention
asks to be pinned). V2 is the only surface where this extractor is load-bearing, so a
model that prefixes placeholder braces (`{name}`, `{a, b}`) can fail every attempt.

**Fix:** Do not commit to the first `{`. Enumerate candidate starts (each `{` index) and
return the first span that `from_json(..., allow_partial=True)` accepts, or prefer the
largest/last balanced block; add a fixture with the literal repro string
`'use {x} then {"a":1}'` per the project's gap-closure convention.

### WR-02: V2 discovery hard-fails on `/api/provider` even though that payload is never read

**File:** `app/llm/opencode_server.py:386-393`

**Issue:** The V2 discovery branch aborts with `reachable=False` when `GET /api/provider`
returns a non-200, yet `parse_v2_models` deliberately ignores `provider_payload` entirely
("its provider-level values … are deliberately NEVER read into a result … The model payload
is authoritative for the pair"). An unrelated 5xx/404 on the provider endpoint therefore
takes down model resolution and, through `_resolve_model`, **every** completion — including
discovery cases the docstring explicitly anticipates ("a cold server can legitimately return
an empty `/api/provider`"). The hard status check makes `/api/model` — the authoritative
source — unusable on its own.

**Fix:** Treat a failed `/api/provider` as non-fatal: pass `{}` (or the empty payload) to
`parse_v2_models` and keep only the `/api/model` status check, or drop the second request
entirely since its result is unused.

### WR-03: README omits the accepted V2 prompt-injection residual it is required to document

**File:** `README.md` (diff adds only the password paragraph)

**Issue:** `docs/runbook-opencode-contract.md:186-189` states the residual is accepted
"on the condition that it is documented here, in `AGENTS.md` and in the `README`", and
`AGENTS.md:354-356` repeats "documented … and the `README`". Only AGENTS.md and the runbook
carry it; the README's "Known limitations"/security prose says nothing about it
(`grep -i injection README.md` → no matches). The stated acceptance condition is unmet, and
AGENTS.md now asserts a documentation state that does not hold.

**Fix:** Add a short "Accepted residual risk" note to README's Known limitations pointing at
`docs/runbook-opencode-contract.md`, or narrow the AGENTS.md/runbook wording to the
locations that actually document it.

## Info

### IN-01: Unused import `INFO_PATH` in the production module (F401)

**File:** `app/llm/opencode_server.py:63`

**Issue:** `INFO_PATH` is imported from `app.llm.contract` but never referenced in this
module (`detection.py` imports its own copy). `ruff check` reports
`F401 app.llm.contract.INFO_PATH imported but unused`. The import was **added by this phase**
(`git show <base>:app/llm/opencode_server.py | grep INFO_PATH` → absent), which contradicts
`deferred-items.md`'s claim that it is "Present at HEAD (682f06d) before this plan's edits".
**Fix:** Remove `INFO_PATH` from the import block.

### IN-02: An `unknown` surface routes discovery down the V1 path, contradicting the fail-closed completion

**File:** `app/llm/opencode_server.py:404-413`

**Issue:** `complete_structured` fails closed on `unknown` (explicit "could not determine the
opencode API surface"), but `discover_models` sends an `unknown` surface to the V1
`/config/providers` path, so the operator sees `unreachable`/`model_not_found` from
discovery instead of the diagnosis the completion path would give. The comment acknowledges
this ("An `unknown` surface falls here").
**Fix:** Either return `reachable=False` with an explicit "unknown surface" error for
`unknown` (matching the completion arm), or document the intentional divergence in
`discover_models`.

### IN-03: A non-JSON 200 from V2 `generate` loses attribution (`attempts=0`)

**File:** `app/llm/opencode_server.py:821` (`_dig(response.json(), …)`)

**Issue:** `response.json()` on a 200 with a non-JSON body raises, escaping to the outer
generic handler → `error_kind` = the exception class name and `attempts = 0`, discarding the
issued count and the per-call identity. The retained V1 arm classifies this explicitly in
`_classify_message_response`, so the two surfaces report the same defect differently.
**Fix:** Wrap the V2 `.json()` calls and return a `_failure(status="error",
error_kind="invalid_response", …)` carrying the current `attempts`, mirroring
`_classify_message_response`.
