<objective>
Make failure a first-class, classified outcome: **every way a structured call can go wrong produces one
of the four legal `llm_calls.status` values plus an operator-facing cause and an attempt count, and a
truncated payload is salvaged only through an explicit allow-list.**

Purpose: success criterion 2 exists because a schema violation that looks like success is the most
expensive failure mode in this pipeline — Phase 5 will rank on this backend, and a silently empty
result would be indistinguishable from a genuine low score. PITFALLS M1 is exactly this pitfall.

Output: the full failure taxonomy inside `OpenCodeServerBackend.complete_structured`, a bounded
client-side retry loop whose ceiling is a `Settings` field, the `_salvage` helper, and the tests that
pin the classification matrix.

**MVP framing — user story (MVP_MODE active):** **As** the local operator, **I want** a failed
structured call to tell me *why* it failed and *how many times* it was tried, **so that** I can tell a
wrong model configuration from a transient network blip without reading server logs.

**Covers:** success criterion 2 in full; PLAT-02's degradation contract.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| opencode response body → `StructuredCallResult` | A partially trusted transport payload, derived from untrusted model output; it must never be persisted verbatim. |
| schema mismatch → operator decision | A laundered mismatch would make an empty result look like a real one. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-3-01 | Tampering | model output filling the schema | high | mitigate | `_salvage` tolerates only an explicit allow-list (`missing`, `int_parsing`); an untolerated mismatch still classifies as `invalid`; `extra="ignore"` applies only to `ProbeResult` while the wire-adjacent models stay `extra="forbid"`. |
| T-3-14 | Tampering | silent degradation masking a real backend fault | high | mitigate | `status` is always one of the four legal values; the cause is carried in `error_kind`; the attempt count comes from the server's own `data.retries` where present and from the recorded request count otherwise; the test asserts `attempts` against the fake's recorded request count so a literal cannot pass. |
| T-3-05 | Information Disclosure | raw response in `error` | medium | mitigate | The non-200 body excerpt is bounded by a module constant; `raw` stays in memory only; the test asserts no credential sentinel reaches `vars(result)` and no branch logs the body. |
| T-3-06 | Denial of Service (self-inflicted) | retry loop | medium | mitigate | Both ceilings are `Settings` fields (`opencode_max_retries`, `opencode_structured_retry_count`) and the loop is an explicit bounded `range`; schema failures are never retried client-side, so the attempt count cannot inflate silently. |
| T-3-SC | Tampering | package installs | low | accept | Zero new packages; `tenacity` is deliberately left unused, and a static assertion forbids importing it in this module. |
</threat_model>
