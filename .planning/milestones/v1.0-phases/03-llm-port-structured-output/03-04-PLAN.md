<objective>
Close D-12's telemetry gap: **the opencode server version becomes a recorded, queryable column on
`llm_calls`, the audit writer grows the reads Phase 5 will share, and the schema guards move
deliberately with the migration.**

Purpose: PITFALLS M9's premise is that a model/version regression must be traceable. `llm_calls`
already carries `provider`/`model`/`agent`/`attempts`/`latency_ms`, but nothing records which server
version produced a call — and `backend`/`error`/`provider` all have distinct meanings that must not be
overloaded. Migration 0003 is one nullable column with a symmetric downgrade.

Output: migration 0003, the ORM mirror, the guard-churn edits, the migrated `llm_calls` audit writer
read helpers, and the repository contract test.

**MVP framing — user story (MVP_MODE active):** **As** the local operator, **I want** every recorded
LLM call to state which opencode version served it, **so that** when a result changes I can tell
whether a server upgrade was the cause.

**Covers:** PLAT-02's auditability obligation (D-12 / M9).
</objective>

  <decision>Apply Alembic migration 0003 adding `llm_calls.server_version` (nullable `VARCHAR(32)`).</decision>
  <context>
    This is a one-way door by the repo's own rule: undoing it needs another migration, and once a later
    migration builds on revision 0003 the reversal cost compounds. The alternative the research
    considered and rejected was overloading an existing text column — `backend` is `String(16)` and
    means "which transport", `error` is the failure cause and is NULL on success (where the version is
    most needed), and `provider` is the provider id. None of them can carry the server version without
    corrupting the field the Phase-5 operator reads.

    Two consequences the reviewer should weigh before approving:
    1. Three assertions in `tests/db/test_migration_contract.py` (`:294`, `:305`, `:500`) name `0002`
       explicitly and must be updated to `0003` in this plan. That is deliberate guard churn, not a
       regression — the exact precedent recorded in `STATE.md` for migration 0002.
    2. `llm_calls` gains no JSON column, so `tests/db/test_no_pii_columns.py:68`'s `"llm_calls":
       frozenset()` allow-list stays unchanged. A `VARCHAR(32)` cannot carry a payload.
  </context>
  <options>
    <option id="migration-0003">
      <name>Add migration 0003 with the nullable column (recommended)</name>
      <pros>Additive, in-place ALTER on SQLite, queryable (`GROUP BY server_version`), no backfill, no data rewrite, symmetric downgrade; the ORM drift guard enforces that the model and migration move together.</pros>
      <cons>Irreversible in one step once later revisions depend on it; three migration-contract assertions must be updated deliberately.</cons>
    </option>
    <option id="reuse-column">
      <name>Record the version in an existing text column</name>
      <pros>No migration at all.</pros>
      <cons>Every candidate column has a distinct meaning another surface already relies on; it would be unqueryable and would corrupt `error`/`backend` for the Phase-5 operator; the version is needed on successful rows where `error` is NULL.</cons>
    </option>
  </options>
  <resume-signal>Select: migration-0003, or reuse-column (which requires replanning Task 2 and Task 3)</resume-signal>
</task>
