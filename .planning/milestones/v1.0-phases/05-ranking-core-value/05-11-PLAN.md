<objective>
Close gap G-05-3: the queue's paging affordance is forward-only. The forward control performs an `hx-swap="innerHTML"` replacement of `#queue-list` with only the next offset's rows, so the label promises "Load more" while the behaviour is "go to the next page" — the rows already on screen are destroyed. No previous/back control exists anywhere, no `hx-push-url`/`hx-history` is present so browser history cannot restore a prior offset either, and the UI renders only the grand total (`N listings`) — never the offset, page size, page index or page count. `QueuePage` already carries `rows/total/offset/limit/has_more/query` plus `next_offset`, and `GET /queue/list` already accepts an arbitrary offset, so the whole fix is derived accessors plus rendering.

Purpose: the queue is the Core Value screen — "one ranked, explained queue" the user acts on. A queue that can only be walked forward is not browsable; a user who cannot tell which slice they are on cannot reason about how much of the corpus they have seen.

Output: `QueuePage` gains `has_prev` / `prev_offset` / `page_index` / `page_count`; the shared fragment renders a Previous / position-line / Next pager in place of the forward-only control; the page size stays server-fixed and is now shown; and the paging test encodes the two-way behaviour.
</objective>

<design_decision>
## Chosen route: explicit page navigation (Previous / position line / Next), replacing the forward-only control

**The user's words decide it.** The report was: *"we should have paginated responses and a ui way to show what page we're on and how many jobs per page."* That is a **page model with a position indicator**, not an accumulating list. An append-style control cannot honestly say "what page we're on" — it has no page, only a growing slice — so it would satisfy at best half the request. The chosen route answers both halves literally: `Page 2 of 3 (25 per page)`.

**It is also the lazier route.** The `innerHTML` swap is not itself wrong — it is wrong only because the control pretends to append. Once each slice IS a page, replacing the page is correct. So the fix is: four derived accessors on the existing dataclass, one rewritten template block, two id-scoped CSS rules, and one rewritten test. No new route (`GET /queue/list` already takes any offset), no new state, no htmx history, no JavaScript.

**Why not append-into-`#queue-list` (the 02-RESEARCH.md:672 intent).** Append would require a second swap target for rows only, dedup discipline around the stable `listing-row-{id}` ids, a separate "showing X–Y of N" position model bolted alongside, and a decision about what the page size means when the list grows unbounded. It also makes the empty/threshold/filter interactions harder (a filter change mid-accumulation). That is strictly more machinery for a strictly weaker answer to the user's sentence. The original append intent is recorded as drifted, not re-imposed.

**No htmx history.** Adding a URL push to a fragment request would put `/queue/list?...` in the address bar; reloading it renders a bare fragment with no page shell. Pushing a hand-built page URL instead would need the same treatment on every filter control and on the POST actions, for a browser-Back affordance the user did not ask for. The in-page Previous control is the backward navigation the gap's `missing` list allows ("a previous/back control **or** htmx history integration").

**Scope fence.** `app/web/routes.py` and `app/config.py` are named in the gap's artifacts but are NOT modified: the route already passes the whole `page` object into the context and already fixes `limit` from settings, and the page size is displayed from `page.limit` — so surfacing it needs no config or route change, and the server-fixed decision (T-02-28) is left exactly as it is.
</design_decision>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| request query string → `parse_queue_query` | The client supplies `offset` (and may try to supply `limit`) |
| `QueuePage` integers → pager markup | Derived page index/offset values cross into `hx-get` URLs and rendered text |
| pager `hx-get` → `GET /queue/list` | A fragment request re-enters the same read path |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-05-39 | Tampering | `parse_queue_query` / the pager request | medium | mitigate | `limit` remains fixed by `settings.queue_page_size` and is never read from the request (T-02-28 unchanged); the position line only displays `page.limit`, and a new test pins that `?limit=1` still returns the server page size. `offset` stays clamped at `max(0, ...)`. |
| T-05-40 | Tampering | pager `hx-get` URLs | low | mitigate | Every pager value is an integer derived from integers already validated at the read boundary, and the URL is built by `QueueQuery.query_string`, which `urlencode`s; the template auto-escapes, so no attribute can be broken out of. No user-controlled string is concatenated into the attribute. |
| T-05-41 | Denial of Service | deep `offset` on the score path | low | accept | A client-supplied offset already existed before this plan and the score path is bounded by `SCORE_SORT_SCAN_LIMIT`; this plan adds no unbounded work — the pager only re-issues the same read the user is already performing. Accepted at personal, single-operator scale (the existing posture). |
| T-05-42 | Information Disclosure | position line | low | accept | The line renders three integers and no listing, CV or path content. Accepted. |
| T-05-SC | Tampering | npm/pip/cargo installs | high | mitigate | This plan installs no package: it edits one repository module, two templates, one committed stylesheet and one test file, all on the existing stack. |
