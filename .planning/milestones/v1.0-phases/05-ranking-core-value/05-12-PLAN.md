<objective>
Close gap G-05-8: the job detail page's Save and Hide controls are silent no-ops, and saved jobs are not discoverable from where they are saved.

The detail page copied the queue row's two action forms verbatim, including `hx-target="#listing-row-{id}"` — an element rendered only by `_listing_row.html` on the queue. The detail page renders no such element, so htmx cannot resolve the target and raises `htmx:targetError`; the POST still reaches `app/api/events.py`, appends the event and returns the row fragment with HTTP 200, but the fragment is never swapped in, so the page shows nothing until a manual reload. Separately, the only saved view is the queue's `Saved` checkbox (`/?saved=1`); the detail page links to nothing, so a user who just clicked Save cannot find where saved jobs go.

Purpose: the detail page is the surface where a listing is judged and acted on. A control that silently does nothing is worse than no control — the user cannot tell whether their action was recorded. The two facets named by the gap (feedback and discoverability) are one coherent fix: make the detail action a real inline swap, and give it a visible state plus a path to the saved view.

Output: a shared `_action_forms.html` that both surfaces include; a `_detail_actions.html` section that is the detail page's swap root and carries the state indicators and the saved-view link; an allow-listed `surface` field on the events route that returns the detail fragment for a detail-originated action; and the regression tests that would have caught the original mismatch.
</objective>

<design_decision>
## Chosen route: a surface-aware fragment from the SAME endpoint, rendered by one shared action-form partial

**The user's words decide the posture.** The report was: *"there's no feedback, when i click save or hide nothing happens which makes it uninituative. Also where are the saved jobs going to?"* A silent no-op is not an acceptable interaction, and a manual reload the user was never told to perform is not feedback. The detail page must show its new state as a result of the click.

**Why a hidden `surface` field and not the `HX-Target` header.** htmx does send an `HX-Target` header automatically, and the route could branch on it — but a header-driven render choice is implicit and awkward to pin from the test client. A hidden field is explicit, travels with the other form fields exactly as `event_type` already does, and can be allow-listed so no unlisted value selects an unknown template. The route reads it, validates it against `ACTION_SURFACES`, and defaults to `queue`.

**Why the same endpoint and not a detail route.** `POST /listings/{id}/events` is the single writer of `listing_events`, and its row response is what keeps the queue's swap honest. A second route would duplicate the write and the `read_row` re-render, and the two could drift — the same class of defect being fixed here. The endpoint already returns a fragment; this plan teaches it to return the right fragment for the surface that asked.

**Why one shared partial.** The bug shipped because the detail page copied the queue row's block verbatim and carried a target that only exists on the queue. Extracting the two controls into `_action_forms.html`, included by both `_listing_row.html` and `_detail_actions.html`, makes that specific drift structurally impossible and matches the project's one-rendering-path rule (T-02-38 / T-05-16).

**Why not a reload-only posture.** A deliberate reload design would still have to show the user something after the click — the POST returns HTML, not a redirect — so it would need the same fragment machinery, with worse ergonomics. The inline swap is the smaller, honest answer.

**Why a link and not a saved count.** A correct saved count would have to reproduce `read_queue`'s inherent gates (hidden, absorbed-twin, latest-run exclusion) or it would disagree with the view it advertises. The gap permits a link/hint; the link goes to the existing filtered view, whose own `N listings` line is the count.

**Scope fence.** The queue's `Saved` checkbox label is untouched (the gap scopes the affordance to the detail page), and `static/vendor/app.css` is untouched: the fragment reuses the existing `badge`/`badge-saved`/`badge-hidden` tokens and gives the link an id only, so no new class token is introduced and `tests/test_stylesheet_coverage.py` needs no new exemption.
</design_decision>
