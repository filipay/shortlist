<objective>
Close gap G-05-1: today the ranking pass's outcome is never persisted, so the queue strip is gated on `ranked_count is not None`, and "ranking is running", "ranking was skipped" and "nothing was attempted" are literally the same rendering (a blank strip). The root cause is that `_finish` (app/pipeline/run.py:591/610/616) is the SOLE writer of the three free-form JSON columns and runs detached from — and independently of — the ranking task (D-88), so any marker the task writes beforehand is clobbered wholesale; `runs.ranked_count` is written only at the end of a successful `run_ranking` (rank.py:487) and stays NULL on every skip path, on the no-candidates gate and on a mid-pass crash.

Purpose: the strip is the Core Value screen's own progress statement. A user who cannot tell a running pass from a skipped one cannot act on the queue; the reported symptom was literally "queue remains unranked, i don't know why" / "i have no indication if the ranking is running".

Output: the ranking outcome is computed synchronously in `run_pipeline` and persisted by `_finish` inside `reason_counts_json`; `RunSummary` reads it back and derives the five states; the queue strip renders each one with an honest human reason; and the reason vocabulary lives in exactly one place.
</objective>

<fix_route_and_staleness>
## Chosen fix route: reuse `reason_counts_json`, single writer, derive `running`

**Storage: reuse.** `runs.reason_counts_json` is a `Column(JSON)` with no CHECK constraint (app/db/models.py), already written wholesale by `_finish` on every run. A `ranking` sub-key is ignored by every existing reader (`run_counts_for` reads named keys; `RunSummary` reads `survivors`; `runs.html` renders the stage log, not this bag). A dedicated `ranking_status` / `ranking_reason` column was rejected: it would cost one Alembic revision (`0005`) plus updates to the two pinned migration-contract tests, in exchange for letting the detached task write directly — which this plan does not need, because the reason is synchronously knowable before `_finish`. No migration, no new column.

**Writer: `_finish` only.** The marker is computed in `run_pipeline`'s ranking block and merged into the `reason_counts` payload handed to `_finish`. `_finish` already assigns `run.reason_counts_json = reason_counts or None` in the same commit as `status`/`finished_at`, so there is exactly one writer and one commit. `_finish` itself is not edited.

**Staleness: `running` is derived, never persisted.** `rank.py:31-34` states that startup recovery is deliberately absent: an interrupted ranking task leaves a NULL `ranked_count`. A persisted `running` marker would therefore read "Ranking in progress" forever after a crash. This plan persists only the terminal outcomes a synchronous precheck can prove (`skipped:<reason>`, `not_attempted`), and derives `running` at render time from the live single-flight task (`ranking_in_progress()`). After a crash or a process restart the marker is absent and the state degrades to `unknown` ("Ranking has not completed for the last run.") — never to a permanent in-progress claim. This also keeps D-88's refresh-only rule: no polling, no SSE, no new poll target; the live-task read is a render-time snapshot.

**Why the task is still started on a skip.** `tests/pipeline/test_finish_llm_counters.py:145-175` exists to prove the ranking task entry point IS reached with an absent fact store (so a future reader cannot argue the LLM caller was never wired). The precheck therefore RECORDS the reason without preventing the start: `run_ranking` still runs and returns immediately on its own guard, exactly as today. The cost is one extra small file read per run (the CV fact store is read once by the precheck and once by the task); the CV document is a few kilobytes and this buys the single-writer rule and the preserved test.

**No logging from the precheck.** `run_ranking` keeps emitting the one `pipeline.rank_skipped` line, so `tests/pipeline/test_rank_optional.py:143-147` (which asserts on that event inside a capture spanning the run) still passes and the log is not duplicated.

**Out of scope, declared.** The open advisories in `05-REVIEW.md` (including WR-04's refusal-row spend accounting and the other warning-level findings) are NOT addressed here: no gap fix requires touching them, and this plan changes no refusal decision, no spend counting and no audit-row shape. The refusal path's behaviour is byte-for-byte unchanged; only the reason vocabulary it shares is now a constant.
</fix_route_and_staleness>
