<objective>
Add a deterministic, description-derived years-of-experience signal that steers the
existing `seniority` ranking sub-score as a soft hint only — never a hard filter, no
new column, no migration, no extra LLM call, no pre-computed candidate-years number.

Purpose: the listing text often names a years floor that the ranker currently has no
explicit sight of; surfacing it (with its source fragment) lets the `seniority` factor
weigh the stated requirement against the CV's evidenced date ranges, and lets the
rationale name a shortfall honestly. The design is settled by prior research and a
design review — this plan encodes it; it does not reopen it.

Output: `required_experience_years()` and `required_experience_fragment()` in
`app/domain/listing.py`; `_required_experience_hint()` wired into
`build_ranking_parts()` in `app/pipeline/rank.py`; focused tests for both.
</objective>

    - required_experience_years(None) is None; required_experience_years("Build the thing.") is None
    - required_experience_fragment("3-5 years of experience") is a non-empty substring of that same description
    - build_ranking_parts(...) over a listing whose description states "5+ years required" returns a hint part in the user turn naming the floor and quoting the matched fragment, and the assembled text still contains the listing block
    - stub.calls[0]["system"] == RANK_SYSTEM_PROMPT on every ranking call (equality, not a grep) — the hint never reaches the system turn
  </behavior>
  <action>
    In app/domain/listing.py, beside the salary section: add a module-level compiled regex (same style as the existing WHITESPACE_RE / PUNCTUATION_RE constants) whose leading captured group is a one- or two-digit number with an optional decimal, optionally followed by a plus-sign-or-"plus" tail and an optional range tail (an en/em dash or the word "to" followed by a second number), then a "year"/"years"/"yr"/"yrs" word. The leading captured group is the required floor. Keep the module pure: standard library `re` only, no I/O (tests/test_import_discipline.py guards this).

    Add `required_experience_years(description: str | None) -> int | None` and `required_experience_fragment(description: str | None) -> str | None`. Both must derive from a single private matcher so the two can never drift. For each candidate match, compute the clause around it by splitting on commas, semicolons, sentence ends, newlines and the words "and"/"but"; casefold that clause and SKIP the match when it contains preferred, ideally, desirable, nice to have, advantage, beneficial, an asset, bonus, or the phrase "a plus" — this is the designated not-required class (the single biggest error class in published extraction pipelines). Return the floor of the first surviving match; return None when there is no surviving match or when the floor is not greater than zero (an explicit "0-2 years" is no usable signal, and absence is NEVER zero required). `required_experience_fragment` returns the exact matched substring from the description, so the anti-fabrication rule holds and a misread is visible rather than silent. Add both names to `__all__`.

    In app/pipeline/rank.py, add `_required_experience_hint(listing: Any) -> str | None` immediately beside `_work_mode_hint`. It reads `getattr(listing, "description", None)` only, returns None when the helper finds no signal, and otherwise returns one user-turn sentence that: names the stated floor and quotes the matched fragment; tells the model to weigh the candidate's evidenced experience against that floor when judging the `seniority` factor; states a shortfall may only lower the `seniority` sub-score and must be named in the rationale; and states explicitly that this is not a hard filter and the listing must stay in the queue. In `build_ranking_parts`, append the returned hint to the existing parts list beside the `_work_mode_hint` append — parts (user turn) only, never the system turn.

    Do NOT touch the rubric factor list, `app/domain/schemas/ranking.py`, the default weights, `RANK_SYSTEM_PROMPT`, `RUBRIC_VERSION` or `app/pipeline/filter_stage.py`. No new dependency, no Alembic migration, no new LLM call, no pre-computed candidate-years number.
